# 일머리 (Ilmeori)

**인수인계 자동화 플랫폼**
2026 화성시 AI·DATA 공모전 지정과제 **N7** 「부서 간 협업 업무공유 플랫폼」 · 내부 행정혁신형

> **파일은 넘겨받는데, 일머리는 못 넘겨받습니다.**

**평소 결재와 대화가 쌓이면, 근거가 붙은 한/글 결재문서와 법정 인계서가 저절로 나옵니다.**

위 두 줄은 하는 일이 다르다. 첫 줄은 **문제**를 말하고 둘째 줄은 **제품**을 말한다. 1차예선 심사평이 "핵심 기능을 한 줄로 소개할 수 있어야 한다"고 짚었는데, 그때 이 자리에는 첫 줄만 있었다 — 처음 보는 사람은 문제에 공감하고도 무엇을 하는 물건인지 모른 채 넘어간다. 둘째 줄은 로그인 화면·`layout.tsx`의 메타·발표 대본에서 **토씨까지 같은 문장**으로 나온다.

**[▶ 배포된 웹앱 — ilmeori.vercel.app](https://ilmeori.vercel.app)** · 가입 없이 데모 계정 4개로 바로 들어갑니다.

## 무엇을 푸는가

화성시 공무원의 업무자료는 **개인 PC와 개인 폴더**에 있다. 협조하려면 파일을 메신저·전화·공문으로 주고받고, 누가 최신본을 갖고 있는지 아무도 확신하지 못한다. 진행상황은 담당자에게 물어봐야만 알 수 있다.

민간 협업도구를 쓰면 되지 않느냐는 물음에 대해서는 정직하게 답한다. 제도는 이미 바뀌었다. 「국가 정보보안 기본지침」 제40조(망분리)는 2026년 5월 1일자로 삭제되었고 국가정보원 스스로 "망분리를 적용한 공공기관은 11%"라고 밝힌 바 있다.

문제는 제도가 아니라 **현장의 실행 격차**다. 2026년 KISA의 N2SF 도입지원 수요기관 6곳 중 지자체는 0곳이다. 지침은 바뀌었지만 담당자의 PC 환경, 조달 절차, 감사 관행은 그대로다. 그 사이에서 실제로 벌어지는 일은 단순하다 — 개인 폴더와 메신저로 버틴다.

> 문제의 본질은 *"민간에 이미 있는 것을 또 만드는 것"*이 아니라,
> **"제도가 허용해도 현장이 아직 옮겨 가지 못한 자리를 메우는 것"**이다.

그리고 이 취약함은 **인사이동** 때 터진다. 평소에도 업무가 개인에게 묶여 있으니, 담당자가 바뀌면 맥락이 통째로 사라진다. 남는 건 정리 안 된 파일 더미와 떠나기 직전 기억으로 급조한 인계서 한 장이다.

담당자가 바뀌면 민원 처리가 지연되고, 작년의 시행착오를 올해 또 반복한다.
**이건 공무원의 편의 문제가 아니라 행정 연속성의 문제이며, 곧 시민이 받는 서비스의 품질 문제다.**

## 설계 원리

> **평소 협업의 부산물이 곧 인수인계서가 된다.**

인수인계를 위해 따로 무언가를 쓰게 하지 않는다. 평소의 협업 기록(진행상태·메모·변경이력·문서)이 그대로 인계 자료가 되도록 구조를 짰다.

## 과제 요구사항 대응

| 과제 요구 | 구현 |
|---|---|
| 문서·업무 공동편집 | 업무 카드 문서를 **섹션 단위로 분할 편집** + 편집 중 잠금 |
| 진행상태 관리 | 업무 상태(대기/진행중/검토/완료) + 칸반 보드 |
| 변경이력 기록 | 모든 사건을 **DB 트리거가 자동 기록** (append-only) |
| 접근권한 관리 | 업무별 역할(소유/편집/열람)을 **RLS로 DB가 강제** |
| 실시간 공유 체계 | 변경 즉시 반영 + 접속자 표시. **채널 권한도 같은 RLS 함수가 지킨다** |
| 팀 단위 협업 | 업무 보드 · 댓글 · 첨부파일 |
| 업무 인수인계 | 담당 업무 일괄 이관 + **규칙 기반** 인수인계서 초안 생성 (모델을 호출하지 않는다) |

과제 요구에는 없지만 **결재**를 넣었다. 현직 관리자 자문의 첫 문장이 「결재라인 어디갔어」였기 때문이다 — 아래 [결재](#결재--공무원이-협업-도구를-안-쓰는-이유) 절에 자리를 어떻게 나눴는지 적었다.

## 화면

| 경로 | 하는 일 |
|---|---|
| `/login` | 가입 없이 **데모 계정 4개 원클릭 입장**. 계정마다 소속·역할이 달라 보이는 업무가 실제로 다르다 |
| `/` | 지연·마감 임박 업무, **내 차례인 결재**, 내 업무에서 남이 움직인 일, 다가오는 마감 |
| `/works` | 상태 4열 칸반. 검색·부서·내 업무·지연 필터가 **전부 주소에 남는다**(공유·새로고침 가능) |
| `/works/[id]` | 문서(섹션 잠금) · 대화 · **결재** · 이력 타임라인 · 참여자·권한 5개 탭. 탭도 주소로 움직인다 |
| `/approvals` | 결재함. 대기·예정·처리·기안 중·완료·전체. **대기에만 숫자가 붙는다** — 그것만이 지금 내가 해야 할 일이다 |
| `/approvals/[id]` | 결재란 · 본문 · 의견. 차례가 오면 서명·반려 상자가 그 자리에 나타난다 |
| `/approvals/[id]/export` | **「온나라로 넘기기」.** 한/글 파일(.hwpx)로 내려받되 **문장마다 어느 기록에서 나왔는지가 함께 실린다** |
| `/handover` | 「업무인계·인수서」 초안 → 확인 → 실행. 실행하면 권한이 실제로 옮겨 간다 |
| `/notes` | 쪽지. 업무를 볼 수 없는 사람에게 묻고, **그 문답이 업무에 남아 인계서까지 간다** |
| `/notifications` | 알림. **읽으면 끝나는 것만** 모인다 — 처리해야 사라지는 것(내 차례 결재·지연)은 결재함과 보드에 그대로 있다 |
| `/org` | 조직도. 실·국 19 → 과 70 → 사람. **이름을 누르면 연락처 카드가 뜬다** — 여는 것도 닫는 것도 링크라 스크립트 없이 동작한다 |
| `/me` | 내 프로필. 못 고치는 것(소속·직급·이메일) · 고치는 것(연락처) · **신청해야 바뀌는 것**(부서 이동)이 갈려 있다 |
| `/people/[id]` | 남의 프로필. 개인 휴대전화는 **본인이 공개한 경우에만** 보인다 — 감추는 것이 아니라 정책이 행을 안 준다 |
| `/audit` | 열람기록. 사용자에게 쓰기 권한이 없는 표. **본인이 연 것만 나온다** — 정책이 그렇게 정해 두었다 |

> `/method`(「자동 생성과 검증」)는 지웠다. 그 화면이 답하던 것은 **심사장의
> 질문**(「AI 어디 있어요」·「이거 진짜 돌아요」)이지 일하는 사람의 질문이
> 아니었고, 화면 하나를 위해 옆줄에 메뉴 묶음을 통째로 세우고 있었다.
> 같은 내용은 이 README 와 `docs/발표대본.md` 가 맡는다.

다섯 가지를 UI에서 특히 붙들었다.

**① 「작년 이맘때」** — 해마다 반복되는 업무에는 작년 판이 옆에 붙는다. 링크만 걸지 않고 작년에 무엇을 남겼는지(문서 항목·첨부 수·마지막 작업일)까지 보여 준다. 링크만 있으면 아무도 누르지 않는다.

**② 인계서의 근거 표시** — 초안의 모든 항목에 "어느 기록에서 나왔는지"를 칩으로 붙였다. 인계자가 확인해야 할 것은 문장이 매끄러운가가 아니라 근거가 맞는가다. 채울 근거가 없는 항목(물품·예산)은 지어내지 않고 "사람이 직접 적어야 합니다"라고 비워 둔다. **그리고 그 자리에서 직접 적을 수 있다** — 규칙이 뽑은 문단은 고쳐 쓰지 못하게 두고(덮어쓰면 그 문장이 근거를 잃는다), 사람이 적은 것은 「인계자 보충」으로 누가 언제 적었는지와 함께 따로 붙는다. 화면에서도 종이에서도 둘이 구별된다.

**③ 색만으로 알리지 않기** — 지연은 붉은 왼쪽 띠 + 배지 글자 + 남은 일수 세 곳에서 알린다. 상태 배지에는 점과 함께 항상 글자가 붙는다.

**④ 화면·종이·파일이 같은 모델에서 나온다** — 결재 문서를 내보내면 화면에서 본 것, Ctrl+P로 나오는 A4, 내려받은 `.hwpx` 셋이 **같은 조립 결과**(`ApprovalExport`)를 그린다. 셋이 각자 조립하면 반드시 어긋나고, 근거를 붙이려고 만든 장치가 셋 중 하나에서 다른 말을 하는 순간 그 꼬리표는 그 자리에서 거짓이 된다.

**⑤ 한 화면에 1등은 하나** — 1차예선 심사평이 「대시보드가 전부 평평해서 무엇이 핵심이고 무엇이 보조인지 눈에 안 들어온다」고 짚었다. 코드를 세어 보니 그 말이 맞았다.

- 화면 글자의 **89%가 15px·13px 두 종류**였다(`text-body-sm` 175곳 + `text-body-xs` 156곳). 7단계 스케일을 정의해 놓고 하위 2단계만 쓰고 있었다.
- 판 제목이 `text-h4`(17px)였는데 그건 **본문과 같은 크기**다. 판 넷이 완전히 같은 스펙(`border-gray-10 + bg-surface`)이라 위계를 만드는 축 여섯(크기·굵기·대비·여백·위치·깊이) 중 **위치 하나만** 쓰고 있었다.
- 업무 보드 한 장에 **색이 12개**였고, 그중 다섯이 아바타였다. 화면에서 채도가 가장 높은 자리가 그 화면에서 가장 덜 중요한 정보였다는 뜻이다.
- 홈에서 가장 큰 글자(32px)는 「○○○ 님, 안녕하세요」였고, 가장 급한 사실(「26일 지남」)은 13px였다. 시선이 안 가는 게 아니라 **틀린 곳으로** 가고 있었다.

그래서 색을 넷으로 묶고(먹색 / HS Blue = 누를 것 / 빨강 = 지금 문제 / HS Orange = 내 차례), 판을 세 등급으로 나누고(`hero` / `default` / `quiet` — [`ui/card.tsx`](src/components/ui/card.tsx)), 홈은 **가장 급한 한 건만** 크게 그린다([`work/urgent-hero.tsx`](src/components/work/urgent-hero.tsx)). 32px은 인사말에서 기한으로 옮겼다.

고쳤는지는 **실눈 시험**으로 잰다 — 첫 화면에 8px 블러를 먹여 덩어리가 하나로 서는지 본다(`npm run test:squint`). 홈의 지배도가 **1.34 → 1.67**(문턱 1.5)로 올랐고, 흐린 판 before/after가 [`docs/screenshots/squint-*`](docs/screenshots/)에 남는다.

### 접근성

개발 중 axe-core(WCAG 2.1 AA + best-practice)를 10개 화면에 돌리며 고쳤다. 그때 실제로 잡힌 것들:

- 상태색을 같은 계열 옅은 배경에 글자로 얹으면 대비가 4.1:1 근처였다 → 글자 전용 색을 따로 뒀다
- `text-body-sm` 같은 커스텀 크기 토큰을 tailwind-merge가 **글자색으로 오인**해 `text-white`를 지우고 있었다. 기본 버튼 글자가 파란 바탕에 검은색(1.78:1)으로 렌더링됐다 → `cn()`에 토큰을 등록해 해결
- 닫힌 모바일 서랍이 탭 순서에 남아 있었다 → `visibility`로 처리(자바스크립트가 없어도 동작)

> 🟡 **그 검사는 저장소에 없었다 — 절반을 갚았다.** 여기에 「위반 0건」이라고 적혀 있었는데 그 숫자를 다시 뽑을 코드가 `npm run check` 어디에도 없었다. 색을 12개에서 4개로 줄이면서 명도 대비만은 다시 잴 수 있게 했다 — `npm run test:contrast`가 `globals.css`에서 색값을 직접 읽어 **29쌍**을 재고, `check`에 들어가 있다.
>
> 처음 돌렸을 때 **주석 두 개가 서로 다른 값을 말하고 있는 것**이 잡혔다. `gray-50`을 두고 한쪽은 4.6:1, 한쪽은 4.32:1이라고 적어 두었는데 맞는 쪽은 4.32였고, 그 사이 홈의 「0 건」 글자가 미달인 채로 떠 있었다. 주석에 박아 둔 숫자가 왜 위험한지가 그대로 드러난 자리라 지금은 실측값을 주석에 적지 않는다.
>
> 아직 안 갚은 것: axe-core가 보던 나머지(레이블·역할·탭 순서 등)는 여전히 자동으로 돌지 않는다. 대비만 세고 나머지는 세지 않는다.

## 결재 — 공무원이 협업 도구를 안 쓰는 이유

현직 관리자 자문에서 나온 첫 문장이 **「결재라인 어디갔어」**였다. 종이컵 하나를 사도 결재를 올린다. 그러니까 결재가 없으면 이 제품을 열어 볼 이유 자체가 없다.

**다만 온나라를 대체하지 않는다.** 「행정업무의 운영 및 혁신에 관한 규정」 시행규칙 제3조제3항이 서식을 나눈다.

| 서식 | 쓰임 | 결재는 어디서 | 본문 초안은 |
|---|---|---|---|
| 별지 제1호서식 | 발신문서 | 온나라. GPKI 서명이 붙는다 | 온나라 |
| **별지 제2호서식** | **발신할 필요가 없는 내부결재문서** | 온나라도 받는다(문서관리카드) | **여기** |
| 별지 제12호서식 | 업무인계·인수서 | 온나라 인계인수(고시 제2024-28호 제8장) | **여기** |

**칸을 새로 만든 게 아니다.** 두 칸 다 온나라에 이미 있다 — 인계인수는 고시 제8장이 통째로 그것이고 별지 제12호서식까지 지목한다. 없는 것은 **그 칸을 원문 기록에서 채우는 방법**이다. 고시 제8장 전문에 '자동생성'·'초안'·'추출'이 한 번도 나오지 않고, 조문은 전부 「~을 등록할 수 있는 기능을 제공」이다.

받는 것은 제4조제6항이 말하는 결문의 **「검토·협조」층**이다. 대외로 나가는 문서는 여기서 만든 것을 온나라로 넘겨 거기서 서명한다.

- **결재유형 8가지** 기안·결재·최종결재·전결·대결·순차협조·병렬협조·사후보고. 「행정업무의 운영 및 혁신에 관한 규정」 제10조(결재·전결·대결)와 시행규칙 제4조(검토·협조)의 낱말을 그대로 쓴다. **온나라 고시(제2024-28호)가 세는 8종과 목록이 같지는 않다** — 거기에는 「검토」·「전대결」이 있고 여기에는 「최종결재」·「사후보고」가 있다
- **결재선 자동 생성** — 기안자 위로 같은 부서의 서열(`profile.rank`)을 훑어 팀장→과장→국장 순으로 채운다. 협조 부서는 「같은 급과 나란히(병렬)」와 「내부 검토 뒤에(순차)」 두 방식
- **결재선 복사** — 다른 문서의 결재선을 가져오되 내부 결재자는 **우리 부서의 같은 서열로 치환**한다. 그대로 옮기면 우리 과 문서가 남의 과 팀장에게 올라간다
- **문서번호** `HS-협조-20260808-0001` — 상신하는 순간 붙고 그 뒤로 움직이지 않는다
- **진행률 배지** 「진행 중 3/5」. 결재함·업무 상세·홈이 같은 것을 쓴다

> **서명은 손으로 찍히지 않는다.** `approval_step` 에는 UPDATE 권한도 정책도 없다. 서명이 들어가는 길은 `submit` · `sign` · `reject` · `withdraw` 절차 넷뿐이고, 각 절차가 호출자를 다시 확인한다. 상신된 문서의 본문은 얼어붙는다 — 팀장이 서명한 뒤에 기안자가 본문을 고칠 수 있으면 팀장은 자기가 읽지 않은 글에 서명한 것이 되고, 종이 결재에서 그것은 위조다.

결재란에 도장 그림을 넣지 않았다. 시제품에서 인장 이미지는 위조 인상을 주고, 실제로는 아무것도 보증하지 않는다. 서명은 이름과 날짜로만 찍는다.

### 온나라로 넘기기 — 이 제품이 혼자 하는 일

상신된 문서에서 한 번 누르면 **별지 제2호서식 모양의 한/글 파일(.hwpx)** 이 떨어진다. 그런데 파일에는 문서만 실리지 않는다.

```
2. 사전 검토 및 협의
   배도현 주무관 협조 완료 (의견 있음)
      근거: 결재 협조란 서명 · 2026년 8월 7일
   “2027년도 예산 요구서 제출 기한(8/8)과 겹칩니다…”
      근거: 시행규칙 제4조의 「의견 있음」

3. 관련 기록
   “…8월 8일까지 반영본을 받기로 했으니 그때 공유드리겠습니다.”
      근거: 업무 대화 · 박준호 주무관, 2026년 7월 30일 · 약속
```

**온나라에도, 브리티웍스에도, 네이버웍스에도 없는 화면이다.** 그 셋은 결재를 *받는* 곳이지 결재의 근거가 *쌓이는* 곳이 아니라서, 「이 문장은 어디서 나왔느냐」에 답할 재료를 애초에 갖고 있지 않다.

- **근거를 고르는 일은 규칙이 한다.** 모델이 고르면 왜 골랐는지를 문서에 적을 수 없고, 그러면 이 꼬리표는 아무것도 보증하지 못한다. 고른 대화는 요약하지 않고 **원문 그대로** 싣는다
- **인계서보다 좁게 잡는다.** 인계서는 안에서 보는 문서라 「빠뜨리는 실수가 더 비싸다」. 결재 문서는 건물 밖으로 나가므로 반대다 — 상관없는 대화가 「근거」라는 이름표를 달고 실리는 쪽이 훨씬 비싸다
- **기안 중인 문서는 내보내지 않는다.** 번호도 서명도 없는 초안이 결재 문서 모양으로 나가면 결재를 받은 문서처럼 보인다. 화면과 주소 양쪽에서 막는다
- **의존성 0.** ZIP은 `node:zlib`, OWPML은 직접 조립한다(`src/lib/hwpx/pack.ts`). 규격 시험 57건 + 근거 규칙 시험 32건이 `npm run check`에 들어 있다

> ✅ **한/글에서 열리는 것을 확인했다.** 오랫동안 이 자리에는 「아직 확인하지 못했다」가 적혀 있었다 — 이 저장소가 리눅스 컨테이너라 한/글이 없었고, 시험이 지키는 것은 「ZIP이 규격대로인가 · XML이 잘 짜였는가 · 글자가 제자리에 들어갔는가」까지였기 때문이다. 규격 시험 위쪽은 실물로 열어 확인했다.
>
> **인쇄(A4) 폴백은 걷어내지 않는다.** 폴백은 「안 열릴까 봐」만이 아니라 **그 자리에 한/글이 없을 수도 있어서** 있는 것이고, 그건 여전하다.

## 보안

**시제품에는 실제 공문서를 단 한 건도 넣지 않는다.** 배포본의 모든 데이터는 가상이다.

권한은 애플리케이션이 아니라 **데이터베이스가 강제**한다.

- 모든 테이블 RLS `default deny` + `force row level security`
- 테이블 권한(GRANT)과 행 권한(RLS) **이중 방어**
- 이력·열람로그는 **INSERT 권한 자체를 부여하지 않는다.** `SECURITY DEFINER` 트리거·RPC만 기록할 수 있다
- `service_role` 키를 **애플리케이션에서 사용하지 않는다.** 쓰는 순간 RLS 전제가 무너진다
- 첨부파일은 private 버킷 + 단기 만료 signed URL. 공개 URL이 존재하지 않는다
- nonce 기반 CSP + HSTS + `X-Frame-Options: DENY` 등 보안 헤더
- 소속·직급은 본인이 바꿀 수 없다 (부서 변경을 통한 권한 상승 차단)

### 검증

정책이 *존재하는 것*과 *실제로 막는 것*은 다르다. 그래서 실제 Postgres에 사용자를 흉내 내어 접속하는 **행동 테스트 166개**를 짰다.

```bash
npm run db:test
```

```
[2] IDOR — UUID를 알아도 뚫리지 않는다
[4] 이력 위조 — 감사 기록은 손댈 수 없다
[5] 권한 상승 — 소속을 바꿔 남의 부서를 엿볼 수 없다
[6] 섹션 편집 잠금 — DB가 강제한다
[8] 인수인계 — 제품의 클라이맥스
[13] 실시간 — 신호는 나가는가, 그리고 아무에게나 가지는 않는가
[15] 결재 — 서명은 손으로 찍히지 않는다
...
166개 통과 · 0개 실패
```

> 이 테스트가 통과한다는 것은 **애플리케이션 코드에 버그가 있어도 권한 없는 사용자에게 데이터가 나가지 않는다**는 뜻이다.

DB 검사가 재현하지 못하는 것(웹소켓·채널 참가 판정·토큰 전달)은 실제 프로젝트에 붙어서 본다.

```bash
npm run db:realtime    # 실제 계정 셋으로 채널에 붙어 본다
npm run test:realtime  # 창 두 개를 띄워 놓고 — 한쪽이 고치면 다른 쪽이 따라오는지
```

## 기술 스택

| 층 | 선택 |
|---|---|
| 프론트/서버 | Next.js 16 (App Router) · React 19 · TypeScript |
| 데이터 | Supabase — Auth / Postgres + RLS / Realtime / Storage |
| 스타일 | Tailwind CSS v4 + **KRDS 디자인 토큰** |
| 문서 | HWPX(별지 제2호서식) 직접 조립 — **의존성 없음.** ZIP은 `node:zlib`, OWPML은 손으로 |
| 근거 선별 | **규칙표(정규식) 기반.** 어떤 모델도 호출하지 않는다 — LLM SDK 0개, `src/` 안에 외부 `fetch` 0회 |
| 설치 | PWA — 설명서 + 서비스워커(셸만) + 아이콘. **덧붙이는 층이라 없어도 앱이 그대로 돈다** |
| 배포 | Vercel |

> **의존성을 늘리지 않는다는 규칙.** HWPX에 JSZip을, 아이콘에 sharp를 넣지 않았다. 필요한 것은 STORED와 DEFLATE 둘뿐이고 `node:zlib`에 이미 있으며, 아이콘은 사각형과 선분뿐이라 거리함수로 충분하다. 의존성 하나가 늘면 그 하나가 배포에 실려 나가고, 내부망 온프레미스 전환에서 그 하나가 검토 대상이 된다.

### 디자인 시스템

KRDS(대한민국 정부 디자인시스템)의 **토큰을 채택**하되, 전면 준수하지는 않는다.

「디지털 정부서비스 UI/UX 가이드라인」은 법령이 아닌 권고이며 1차 적용 대상은 대국민 서비스다. 이 프로젝트는 로그인 기반 내부 업무 시스템이므로, 대국민 사이트 구조(공식 배너·운영기관 식별자·신청 패턴)를 그대로 적용하면 업무 도구로서 오히려 나빠진다.

체크리스트 자체가 `E(예외)` `N/A(해당없음)` 판정 칸을 두고 있다. 그래서 **취사선택하고 그 판단 근거를 문서화**했다.

- 채택: Pretendard GOV / 본문 17px / 행간 1.5 / 굵기 2단 / KRDS 색상 체계 / 컨테이너 비례 둥글기 / 접근성
- 미적용: 공식 배너 · 운영기관 식별자 · 대국민형 헤더·푸터 · 다크모드

## 개발 환경 설정

### 1. 의존성

```bash
npm install
```

### 2. 바로 실행 (데모 모드)

Supabase 설정이 **없으면 앱은 목업 데이터로 동작한다.**

```bash
npm run dev   # http://localhost:3000
```

화면·흐름은 전부 그대로 돌아가고, 데모 중 바꾼 내용(상태 변경·대화·인계 실행)은 **각자의 브라우저 쿠키**에 담긴다. 서버에는 아무것도 쌓이지 않으므로 시제품 주소에 남는 데이터가 0이다. 심사위원마다 각자의 상태를 갖고, `/handover`의 「시연 처음으로」로 언제든 되돌릴 수 있다.

### 3. Supabase 프로젝트 연결 (선택)

1. [supabase.com](https://supabase.com)에서 프로젝트 생성
2. `.env.local`의 두 줄 주석을 풀고 값 입력

> 두 값 중 하나만 채우면 시작 시 즉시 실패한다. 반쯤 설정된 상태가 제일 위험하다.
>
> ⚠️ `.env.local`은 절대 커밋하지 않는다. 제출물에 깃헙 주소가 포함되므로 키 유출이 가장 현실적인 사고 경로다.

### 4. 마이그레이션과 시드

Supabase 대시보드의 SQL Editor에서 순서대로 실행한다.

```
supabase/migrations/0001_schema.sql      스키마 · 인덱스
supabase/migrations/0002_rls.sql         권한 · RLS 정책 35개
supabase/migrations/0003_triggers.sql    이력 자동기록 · 인계 실행 · Storage
supabase/migrations/0004_hardening.sql   기본 권한 잠금 · 점검용 뷰
...                                      (0005~0011 은 docs/supabase-설정.md 참조)
supabase/migrations/0012_realtime.sql    실시간 공유 — 토픽 정책 · 방송 트리거
supabase/migrations/0013_access_log_session.sql  열람기록을 세션 단위로
supabase/migrations/0014_handover_note.sql       인계서에 인계자가 보태는 칸
supabase/migrations/0015_handover_owner_guard.sql 인계 건의 주인 — 인수자가 가로채지 못하게
supabase/migrations/0016_approval.sql             결재 — 표·결재유형 8종·직급 서열
supabase/migrations/0017_approval_rls.sql         결재의 권한과 절차 (서명은 절차로만 찍힌다)
supabase/seed/demo.sql                   시연 데이터 (생성물)
```

적용 전에 로컬에서 먼저 검증할 수 있다. PGlite(Postgres WASM)로 실제 실행해 본다.

```bash
npm run db:verify      # 마이그레이션이 실제로 도는지
npm run db:test        # RLS가 실제로 막는지 (166개)
npm run db:seed        # src/lib/mock → supabase/seed/demo.sql 생성
npm run db:seed:test   # 시드가 실제로 들어가는지
```

적용 후에는 이걸 돌린다. **0행이어야 정상이다.**

```sql
select * from app.security_audit;
```

대시보드에서 손으로 눌러야 하는 보안 설정(가입 차단·세션·리다이렉트 화이트리스트 등)은
**[docs/supabase-설정.md](docs/supabase-설정.md)** 에 정리해 두었다.

### 전체 점검

```bash
npm run check   # typecheck + safe-next + feedback-url + hwpx(57) + cues(32)
                # + db:verify(44) + db:test(166) + db:seed:test
```

`npm run check` 는 **DB 없이도 전부 돈다**(PGlite로 실제 Postgres를 띄운다). 브라우저가 있는 자리에서는 왕복까지 본다.

```bash
npm run build && npm start &
npm run test:browser    # 거의 전부 자바스크립트를 끈 상태로
npm run test:realtime   # 창 두 개를 띄워 놓고
```

### 리전 — 함수를 DB 옆에 둔다

`vercel.json` 의 `regions: ["icn1"]` 하나가 이 앱에서 가장 큰 성능 결정이다.

Supabase 프로젝트는 서울(ap-northeast-2)에 있는데 Vercel 함수는 기본값대로
미국 동부(iad1)에서 돌고 있었다. 화면 하나가 DB에 십수 번 묻는 구조라
그 거리가 요청마다 곱해졌다.

| 화면 | iad1 | icn1(현재) |
|---|---|---|
| 홈 | 3.6초 | 0.1초 안팎 |
| 업무 상세 | 2.2초 | 0.1초 안팎 |
| 결재함 | 1.2초 | 0.1초 안팎 |

같은 코드·같은 DB다. 실행 위치만 옮겼다.

**맞바꾼 것**: 단일 리전이라 icn1 장애가 곧 전면 장애다. 그리고 이 설정이
묶는 것은 **함수 실행 위치뿐**이다 — CDN 엣지, 빌드 머신, 런타임 로그는
따로 논다. 「개인정보가 국내에만 머문다」는 이 파일 하나로는 주장할 수 없다.

### PWA — 덧붙이는 층

홈 화면에 설치하면 주소창 없는 창 하나로 뜬다. 설치하지 않아도, 서비스워커가 없어도, 자바스크립트가 꺼져 있어도 앱은 **지금까지와 똑같이** 돈다.

**서비스워커가 하지 않는 일이 그 파일의 전부다.** 캐시는 쿠키가 아니라서 로그아웃해도 지워지지 않고, 시청 자리의 컴퓨터는 여러 사람이 쓴다. 화면을 캐시하면 그 공문서는 다음 사람의 브라우저가 그대로 꺼내 볼 수 있다.

| 담는 것 | 안 담는 것 |
|---|---|
| 빌드마다 이름이 바뀌는 스크립트·스타일, 아이콘, 설명서, 「연결이 끊겼습니다」 한 장 | **화면(HTML) · RSC 응답 · 서버 액션 · 첨부파일 · HWPX** — 한 줄도 |

「오프라인에서 업무를 본다」는 할 수 있지만 하지 않는다. 그 판단이 「권한은 DB가 강제한다」와 같은 자리에 있다.
