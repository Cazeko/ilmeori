## 3. 결재 — 데이터 모델 (8/8~9)

### 3.1 마이그레이션

**`0016_approval.sql`**

기존 규약을 따른다 — **표와 열거형은 스키마 없이(`public`), `app`은 RLS 보조 함수 전용**이다.

```sql
-- 직급 서열. 결재선 자동 생성이 이 한 칸에서 나온다.
-- profile.position(주무관/팀장/과장)은 표시용 문자열이고, 서열 판정은 숫자로 한다.
alter table profile add column rank smallint not null default 50;
-- 10 시장 / 20 국장·실장 / 30 과장 / 40 팀장 / 50 주무관

create type approval_kind as enum (
  'draft',        -- 기안
  'review',       -- 결재   (중간결재자)
  'final',        -- 최종결재
  'delegated',    -- 전결
  'acting',       -- 대결
  'concur_seq',   -- 순차협조
  'concur_par',   -- 병렬협조
  'post_report'   -- 사후보고
);

create type approval_state as enum (
  'drafting',     -- 기안 중 (임시저장)
  'in_progress',  -- 진행
  'completed',    -- 완결
  'rejected',     -- 반려
  'withdrawn'     -- 회수 (기안취소)
);

create table approval (
  id            uuid primary key default gen_random_uuid(),
  work_id       uuid not null references work(id) on delete cascade,
  form          text not null,          -- 'report' | 'plan' | 'review' | 'cooperation'
  doc_no        text unique,            -- HS-협조-20260808-0001
  title         text not null,
  body          text not null default '',
  retention     smallint,               -- 보존연한(년)
  security      text not null default 'normal',
  state         approval_state not null default 'drafting',
  drafter_id    uuid not null references profile(id),
  created_at    timestamptz not null default now(),
  -- 결재가 끝난 시각. 「completed_at」이라 이름 붙이면 반려된 문서의 그 칸이 거짓말을 한다.
  closed_at     timestamptz
);

create table approval_step (
  id           uuid primary key default gen_random_uuid(),
  approval_id  uuid not null references approval(id) on delete cascade,
  seq          smallint not null,       -- 결재 순서
  kind         approval_kind not null,
  approver_id  uuid not null references profile(id),
  position     text not null,           -- 서명 당시 직위 (나중에 바뀌어도 문서엔 그대로)
  signed_at    timestamptz,
  rejected_at  timestamptz,             -- 누가 반려했는지도 칸에 남는다
  opinion      text,                    -- 「의견 있음」 — 시행규칙 제4조
  unique (approval_id, seq),
  unique (approval_id, approver_id)
);

-- 기안란은 한 문서에 하나뿐이다. 둘이면 상신 절차가 아무거나 집어 서명하고,
-- 남은 기안란은 아무도 처리할 수 없어 그 문서는 영원히 완결되지 않는다.
create unique index on approval_step (approval_id) where kind = 'draft';
```

> **`position`을 문자열로 박는 이유.** 결재란은 서명한 그 시점의 직위를 남긴다.
> `profile`을 조인해 그리면 인사이동 후에 옛 문서의 결재란이 바뀐다. 그건 문서 위조다.

> **계획과 달라진 것 셋.** `completed_at` → **`closed_at`**(반려된 문서의 칸이
> 거짓말을 하지 않게), `rejected_at` 추가(반려한 사람이 칸에 남게),
> 기안란 부분 유니크 인덱스 추가(검토에서 구멍으로 나왔다).

**`0017_approval_rls.sql`** — 실제로 들어간 모양

- `approval` 읽기: 기안 중이면 기안자만. 상신된 뒤에는 그 업무를 볼 수 있는 사람
  ∪ 결재선에 이름이 있는 사람. **협조자는 업무는 못 봐도 그 문서 한 장은 본다**
- `approval_step` **UPDATE 정책도 권한도 없다.** 서명이 들어가는 길은 절차 넷뿐이다 —
  `submit_approval` · `sign_approval` · `reject_approval` · `withdraw_approval`
  (계획에서는 「자기 칸만 UPDATE」였다. 완결 판정이 두 표에 걸쳐 있어 절차로 옮겼다)
- **완결·반려·회수된 결재는 아무도 못 고친다** — `0011`의 완료된 인계 잠금과 같은 규칙
- **상신된 결재의 본문은 얼어붙는다.** 서명한 사람이 읽지 않은 글에 서명한 것이 되면 위조다
- 결재 사건은 기존 `activity`에 얹는다. 새 이력 표를 만들지 않는다
- 기안 중인 문서는 실시간 신호를 보내지 않는다 — 초안을 쓰고 있다는 사실 자체가 정보다

### 3.2 결재선 자동 생성

```
기안자 → 같은 부서에서 rank가 더 작은 사람을 위로 훑는다
       → 팀장(40) · 과장(30) · 국장(20)
       → 마지막 사람을 'final', 중간을 'review'
협조 부서를 고르면 그 부서의 같은 급을 'concur_seq' 로 끼워 넣는다
```

자문의 *"급을 맞추어 협조"* / *"검토 후 협조"* 두 방식을 옵션으로 둔다.

### 3.3 결재선 복사

*"다른 부서 사람들이 결재한 거 그대로 쓰기 기능, 무조건 있어야 하고"* — 자문에서 「무조건」이 붙은 유일한 요구다.

- 내가 볼 수 있는 결재 문서 목록에서 하나 골라 결재선만 가져온다
- 사람이 그대로 있으면 그대로, 부서가 다르면 **같은 rank의 사람으로 치환**해 제안한다

### 3.4 행동시험 (`supabase/rls.test.mjs`에 [15] 추가)

```
[15] 결재
  · 결재선에 없고 업무도 못 보면 결재 문서가 보이지 않는다
  · 남의 결재칸에 서명할 수 없다
  · 완결된 결재는 기안자도 못 고친다
  · 전결이 찍히면 그 뒤 순서는 서명할 수 없다
  · 문서번호는 중복되지 않는다
```

┌──────────────┬──────────────────────────────────────┐

## 5. HWPX 내보내기 (8/12~13)

### 5.1 방식 — 만들지 않고 갈아 끼운다

```
한/글로 만든 별지 제2호서식 템플릿.hwpx
        │  (ZIP)
        ├─ Contents/section0.xml   ← 여기의 자리표시자만 치환
        ├─ Contents/content.hpf
        └─ …
        │  JSZip 으로 열고 → 치환 → 다시 압축
        ▼
    완성된 .hwpx  →  한/글에서 열린다 (템플릿이 보장한다)
```

**직접 생성하지 않는 이유.** OWPML 명세를 우리가 맞게 썼는지는 한/글로 열어 봐야만 안다.
템플릿 치환이면 검증 문제가 *"우리 XML이 유효한가"*에서 *"글자가 제자리에 들어갔나"*로 줄어든다.

| 후보 | 판단 |
|---|---|
| **템플릿 + JSZip 치환** | **채택.** 서식·표·머리글 보존. 의존성 하나 |
| `@ssabrojs/hwpxjs` | 평문 위주. 표·서식이 필요한 우리 용도엔 부족 |
| `hwpxlib`(Java) | 가장 성숙하나 백엔드 언어가 바뀐다 |

### 5.2 파일

```
src/lib/hwpx/
├── template/별지제2호서식.hwpx     ← 한/글로 직접 만든다
├── pack.ts                        ZIP 열기·치환·다시 압축
└── build-report.ts                기록 → 서식 칸 대응 (handover-draft.ts 와 같은 구조)
```

`buildHandoverDraft()`가 이미 하는 일과 같다. 대응표만 다르다.

### 5.3 검증 (이것이 8/13의 전부)

1. 만든 파일을 **실제 한/글에서 연다**
2. 표가 깨지지 않는가 · 한글이 깨지지 않는가 · 편집이 되는가
3. 안 되면 **인쇄(A4) 폴백**을 선언하고 다음 날을 화면 정비로 돌린다

## 7. 화면 정비 + PWA (8/15)

앞서 논의한 디자인 건을 여기서 한꺼번에 친다.

| 항목 | 내용 |
|---|---|
| 색 두 층 | `--color-white: #fafafa` · `--color-gray-5: #f4f5f6 → #f0f1f2` (명도비 1.09 유지). 인쇄는 순백 유지 |
| 본문 폭 | `PageContainer` 신설 — `mx-auto max-w-[1440px]`. 7개 화면 교체 |
| 헤더 | 로고 / 검색(가운데) / 사용자 3분할 |
| 사이드바 | 간격 넓히고 아이콘 18→20px, 활성 항목에 primary 바 |
| 카드 위계 | 지연 = 붉은 띠 · **D-0~D-1 = 화성 오렌지 띠**(BI 보조색이 처음으로 화면에 나온다) |
| 제목 | `PageHeader` h1을 `text-h2`(24px) → `text-h1`(32px) |
| PWA | `manifest.json` + service worker(셸 캐시만) + 아이콘. **덧붙이는 층이라 JS 없는 동작을 깨지 않는다** |

대비 재계산이 필요하다 — `--color-status-*-text` 5종은 *"흰 배경 4.5:1"* 근거로 만든 값이라
배경이 내려가면 여유가 줄어든다. 측정하고 `globals.css` 주석의 수치도 고친다.

## 8. 회귀 검증 (8/17)

| 시험 | 지금 | 늘어날 것 |
|---|---|---|
| `npm run db:test` | 98 | **+ [15] 결재 12건 내외** |
| `npm run test:browser` | 105 | **+ 결재 왕복 (자바스크립트 끈 상태로)** |
| `npm run db:verify` | 44 | + 새 표·정책 |
| `npm run test:realtime` | 23 | 변동 없음 |

**결재 화면도 자바스크립트 없이 동작해야 한다.** 결재선 지정은 `<select multiple>`과 폼 제출로,
순서 변경은 값이 다른 제출 버튼으로 짠다. 상태 변경 버튼 4개를 그렇게 만든 것과 같은 방식이다.

## 9. 발표에서 말할 순서

1. 문제 — 인사이동이 오면 일머리가 사라진다 (기존)
2. **"그런데 공무원은 협업 도구를 왜 안 쓸까요? 결재가 없으니까요."** ← 자문 인용
3. 그래서 결재를 넣었습니다. **다만 온나라를 대체하지 않습니다**
4. 시행규칙 제3조 — 별지 제1호(발신) vs **제2호(내부결재)**. 우리는 뒤쪽입니다
5. 시연 — 업무 협업 → 검토·협조 → **한글 파일로 떨어짐** → 온나라에 올리면 끝
6. 그리고 그 문서의 모든 문단에 **어느 기록에서 나왔는지가 붙어 있습니다**
7. 인계·인수 (기존 클라이맥스)

**가장 위험한 질문은 4번을 먼저 말하지 않았을 때 온다** — *"그거 온나라에 있는데요?"*
그래서 우리가 먼저 꺼낸다.
