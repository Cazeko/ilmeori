# 쪽지와 알림 — 설계

2026-08-23. 아직 코드는 없다. **무엇을 짓고 무엇을 짓지 않을지**를 정한 문서다.

`docs/발전계획.md` 가 「쪽지」를 2차예선 몫으로 잡아 두었고 `docs/남은작업.md` 가
「알림 — 내 업무가 움직였을 때. 1일」을 적어 두었다. 이 문서는 그 두 줄을 실제
설계로 편다.

## 0. 결정 다섯

| # | 결정 | 한 줄 근거 |
|---|---|---|
| 1 | 메신저가 아니라 **쪽지** | 카톡형 DM 은 지식이 업무 밖으로 새는 통로다 |

| 5 | 부르는 방법은 둘(`@` · 체크박스), **저장되는 것은 하나** | 스크립트 없이도 사람을 부를 수 있어야 한다 |

## 1. 왜 메신저가 아닌가

이 제품이 파는 문장은 하나다 — **「평소 협업의 부산물이 곧 인수인계서가 된다」.**
인계 화면이 그것을 이렇게 적고 있다: *「인계서를 위해 따로 적어 둔 것은 한 줄도
없습니다」.*

카톡형 DM 을 넣는다는 것은 **그 부산물이 빠져나가는 통로를 스스로 파는 일**이다.
DM 에 쌓인 "그거 왜 그렇게 했냐면요"는 인계서에 한 줄도 안 실린다. 담당자가
바뀌는 순간 통째로 사라지고, 그 사라짐이 정확히 이 제품이 없애겠다고 한 것이다.

즉 메신저는 기능이 하나 느는 일이 아니라 **논지가 하나 깎이는 일**이다.

경쟁 제품 조사에서도 같은 결론이 나왔다(`발전계획.md` §0) — 브리티웍스 공공이
카톡형 채팅이 아니라 **쪽지**를 독립 기능으로 유지한다. 공공 조직의 실제 동선이
그쪽이다.

---

## 2. 쪽지가 하는 일 — 다른 과 사람에게 묻기

쪽지가 필요한 이유를 넷으로 놓고 하나만 골랐다.

| 후보 | 판정 |
|---|---|
| 업무를 아직 안 만들었을 때 | ✗ 없어도 굴러간다 |
| **상대가 그 업무 참여자가 아닐 때** | ✅ **여기가 제품 한복판에 뚫린 구멍** |
| 공개로 남기기 곤란할 때 | ✗ 나중에 |
| 업무와 무관한 잡담 | ✗ 안 한다 |

댓글은 공개 범위 안에서만 보인다. 참여자가 아닌 사람에게는 닿지 않는다.
**「부서 간 협업」을 판다면서 부서 밖 사람에게 말 걸 방법이 없었다.**

그리고 이 구멍을 메우면 논지가 깎이는 게 아니라 **뒤집힌다.**

> 카톡으로 물으면 답이 카톡에 남는다. 쪽지로 물으면 **그 문답이 업무에 붙어
> 인계서까지 간다.** 쪽지는 지식을 새게 하는 통로가 아니라 **바깥에 있던 지식을
> 업무 안으로 끌어오는 장치**다.

```
[업무] 전국체전 수송·교통대책 수립
  └ 쪽지 → 안전정책과 박준호 주무관
     "이 구간 통제 협의, 작년에 어디랑 하셨나요?"
     └ 답: "경찰서 교통과요. 담당 바뀌었을 겁니다."
```

이 문답은 쪽지함에도 있고 **업무 상세에도 그대로 있다.** 같은 행을 두 자리에서
보는 것이지 복사가 아니다.

**「업무에 옮기기」 단추는 만들지 않는다.** 누르라고 만들면 안 누르고, 안 누른
문답은 없는 것과 같다. 그리고 그 단추는 정확히 「따로 적는 일」이라 §1 의 문장과
충돌한다.

## 3. 권한 — 물어도 열어 주지 않는다

박 주무관은 그 업무를 **못 본다.** 쪽지에 적힌 만큼만 본다. 업무 링크는 걸리되
권한이 없으면 「열람 권한이 없는 업무」로 뜬다 — **이미 있는 처리**다
(`approval-row.tsx` 가 결재선에 이름은 있고 업무는 못 보는 경우를 그렇게 그린다).

세 갈래를 놓고 골랐다.

| | 어떻게 | 왜 안 골랐나 / 골랐나 |
|---|---|---|
| **A. 안 보여준다** | 쪽지에 적은 만큼만 | ✅ 실제 행정이 그렇다. 공문으로 질의를 보내고, 문서가 필요하면 문서를 따로 보낸다 |
| B. 열람자로 자동 추가 | `work_member(viewer)` 로 넣는다 | ✗ 「참여자 추가는 소유자만」이라는 기존 규칙을 깬다. 참여자면 누구나 권한을 넓히게 된다 |
| C. 소유자에게 열람 요청 | 승인하면 열린다 | ✗ 왕복이 하나 더 는다. 물어보는 데 이틀 걸리면 안 쓴다 |

B·C 는 나중에 얹을 수 있다. **A 를 건너뛰면 되돌리기 어렵다** — 한 번 넓힌
권한은 회수 절차가 따로 필요하다.

## 4. 알림 — 사건만 담는다

이 앱에는 「내가 움직여야 하는 것」을 모으는 자리가 **이미 셋** 있다 — 홈의
히어로, 결재함의 「지금 내 차례」, 홈의 인계 알림. 알림창은 **네 번째 수집기**다.
그러면 "그래서 어딜 봐야 하지"가 다시 생기고, 그것이 1차 심사에서 지적받은 바로
그 증상이다.

규칙 한 줄로 막는다.

> ## 처리해야 사라지는 것은 알림이 아니다.

| | 성질 | 어디에 |
|---|---|---|
| 나를 댓글에서 불렀다 | 사건 — 읽으면 끝난다 | **알림창** |
| 쪽지가 왔다 | 사건 | **알림창** · 쪽지함 |
| 내 업무가 움직였다 | 사건 | **알림창** |
| 내가 올린 문서가 반려됐다 | 사건 | **알림창** |
| 지금 내 차례 결재 | 상태 — 서명해야 사라진다 | 결재함 · 홈 |
| 지연된 업무 | 상태 | 보드 · 홈 |

둘을 한 통에 넣으면 **읽음 처리된 「내 차례 결재」가 알림창에서 사라지는데 일은
그대로 남는다.** 모든 알림 시스템이 실패하는 지점이 여기다.

## 5. 데이터

### 쪽지

```sql
create table note (
  id           uuid primary key default gen_random_uuid(),
  work_id      uuid not null references work(id) on delete cascade,  -- ★
  thread_id    uuid not null,        -- 첫 쪽지의 id. 답장이 같은 실에 묶인다
  author_id    uuid not null references profile(id),
  recipient_id uuid not null references profile(id),
  body         text not null,
  read_at      timestamptz,
  deleted_at   timestamptz,          -- comment 와 같은 소프트 삭제
  created_at   timestamptz not null default now()
);
```

★ **`work_id` 가 `not null` 인 것이 이 설계의 전부다.** 업무 없는 쪽지를 허용하는
순간 §1 에서 막은 통로가 그대로 열린다. 업무를 못 고르면 쪽지도 못 보낸다 —
제약이 아니라 **주장**이다.

`deleted_at` 은 댓글과 맞춘다. 인계서가 읽는 자료라 하드 삭제하면 근거에 구멍이 난다.

### 멘션

`comment.body` 는 그냥 text 다. 여기에 `@김서연` 을 적게 하고 서버가 파싱하면 두
가지가 깨진다 — 김씨가 둘이면 누구인지 모르고, **자동완성은 스크립트가 있어야
뜬다.** 이 앱은 스크립트 없이 전부 도는 것이 전제이고 `tests/browser.test.mjs`
가 그것을 지킨다.

그래서 **부르는 방법을 둘 두고 저장되는 것은 하나로** 한다.

```
┌─ 대화 남기기 ─────────────────────────────┐
│ 이 구간 통제 협의 @박준호|                 │
│              ┌──────────────────────┐     │
│              │ 준 박준호 주무관      │ ← @ 치면 뜬다 (스크립트)
│              │ 서 김서연 주무관      │
│              └──────────────────────┘     │
├───────────────────────────────────────────┤
│ 부를 사람   [박준호 ×]        ← 여기가 진실 │
└───────────────────────────────────────────┘
```

- **스크립트 없을 때** — 「부를 사람」 줄이 참여자 체크박스로 그려진다. `@` 없이도
  부를 수 있다.
- **스크립트 있을 때** — 그 줄이 칩으로 접히고, `@` 를 치면 목록이 뜬다. 고르면
  본문에 `@박준호` 가 박히고 **동시에 그 사람 칩이 켜진다.**

폼이 서버로 보내는 값은 두 경우가 **같다**(`mention=<profileId>`). 서버 코드는 한
갈래, 시험도 한 벌이다.

**「부를 사람」 줄을 눈에 보이게 남기는 이유** — 본문에 `@박준호` 라고 손으로
타이핑만 하면 목록에서 고른 게 아니라서 아무도 안 불린다. 그것이 화면에 안 보이면
**조용히 실패**한다. 알림 기능에서 제일 나쁜 고장이다.

```sql
create table comment_mention (
  comment_id uuid not null references comment(id) on delete cascade,
  profile_id uuid not null references profile(id) on delete cascade,
  primary key (comment_id, profile_id)
);
```

목록에 뜨는 사람: **댓글은 그 업무 참여자만**(댓글을 볼 수 있는 사람만 부를 수
있어야 한다). **쪽지는 전 직원** — 그것이 쪽지의 존재 이유다.

### 알림

`activity` 와 **다른 표**로 둔다. `activity` 는 append-only 감사 기록이고 스키마에
*「사후 조작이 불가능하다」* 고 적혀 있다. 알림은 **배달** 기록이다 — 읽으면
소멸해도 되는 것. 한 표에 넣으면 감사 기록에 `read_at` 이 붙는다.

```sql
create table notification (
  id           bigint generated always as identity primary key,
  recipient_id uuid not null references profile(id) on delete cascade,
  kind         notification_kind not null,   -- mention | note | work_touched | approval_decided
  work_id      uuid references work(id) on delete cascade,
  target_id    uuid,                         -- comment.id · note.id · approval.id
  actor_id     uuid references profile(id),
  summary      text not null,                -- 사람이 읽는 한 줄 (activity 와 같은 규약)
  count        int  not null default 1,      -- 묶인 개수 (§7)
  read_at      timestamptz,
  created_at   timestamptz not null default now()
);
```

**`href` 는 넣지 않는다.** 주소를 DB 에 박으면 라우트를 고칠 때 조용히 썩는다.
앱이 `kind` + `target_id` 로 만든다.

RLS: `recipient_id = auth.uid()` 로 select, `read_at` 만 update. insert 는 트리거
(security definer)만.

## 6. 화면

### 배지 색 — 4갈래가 전부 안 맞는다

| | 왜 안 되나 |
|---|---|
| 🔴 빨강 | 「지연·반려 **둘뿐**」이라고 못박았다 |
| 🟠 주황 | 「내가 움직여야 하는 것」인데 §4 에서 알림은 처리 대상이 아니라고 정했다 |
| 🔵 파랑 | 「누를 수 있는 것」. 머리 줄이 이미 다 파랑이라 안 튄다 |

**답은 색이 아니라 뒤집기다.** 이미 있는 수다 — 대외비 칩이 `bg-gray-90
text-gray-0` 이고 주석에 *「색 대신 뒤집는다 — 뒤집기는 색을 한 개도 쓰지 않으면서
눈에 띄는 유일한 수단」* 이라고 적혀 있다. 안 읽은 수는 **검은 알약에 흰 숫자.**
색 예산을 한 갈래도 안 쓴다.

### 세 자리

**① 머리 줄의 종** — 아바타 왼쪽. `<details>` 로 연다. 이 앱은 모바일 서랍을 이미
그렇게 열고 있어서(*「여는 일은 `<details>` 가 하므로 스크립트 없이 열린다」*)
**무JS 에서 그대로 돈다.** 목록 맨 아래에 「전부 보기」 → `/notifications`.

**② 쪽지함** — 왼쪽 메뉴 「업무」 그룹에 하나. 결재함과 같은 모양(칸 목록 +
스레드)이라 새 어휘가 안 는다.

**③ 업무 상세** — **새 탭을 만들지 않는다.** 이미 다섯이고, 대개 비어 있을 여섯
번째 탭은 소음이다. **「대화」 탭 안**, 댓글 아래에 「바깥에 물어본 것」 구역으로
둔다. 그게 오히려 논지에 맞는다 — 안에서 한 대화와 밖에 물어본 것이 한 화면에
나란히 있고, 인계서는 둘 다 읽는다.

## 7. 알림이 생기는 자리, 그리고 소음

| `kind` | 언제 | 색 |
|---|---|---|
| `mention` | 댓글에서 나를 불렀다 | 무채색 |
| `note` | 쪽지가 왔다 · 답장이 왔다 | 무채색 |
| `work_touched` | 내 업무가 움직였다 | 무채색 |
| `approval_decided` | 내가 올린 문서가 결재/반려됐다 | 반려는 🔴 |

넷째를 넣는 이유: 「내 차례 결재」는 상태라 뺐지만 **반려는 사건**이다. 결재함은
문서 목록일 뿐 "반려됐다"고 소리치지 않는다. 그리고 여기가 알림 목록에서
**빨강이 허용되는 유일한 자리**다 — 「지연·반려 둘뿐」과 정확히 맞는다.

**소음이 이 기능을 죽인다.** `activity` 는 7갈래로 뛴다(`realtime.ts` 의
`TOUCH_KINDS`). 6명짜리 업무 하나가 하루에 알림 스무 줄을 만들면 아무도 안 본다.

1. **내가 한 일은 나에게 안 간다** — `actor_id = recipient_id` 이면 만들지 않는다
2. **안 읽은 것이 있으면 묶는다** — 같은 업무·같은 갈래로 안 읽은 줄이 있으면 새로
   만들지 않고 `count` 를 올린다. *「전국체전 수송대책 — 오늘 3건 움직임」*
3. **`mention`·`note` 는 안 묶는다** — 사람이 나를 부른 것은 한 건씩 다 보여야 한다

## 8. 읽음과 실시간

**읽음은 누른 것만.** 종을 열었다고 읽은 게 아니다 — 열어 보고 "나중에 봐야지"
하는 것이 정상 동선이다. 「전부 읽음」 단추를 하나 둔다.

무JS 로 「누르면 읽음」을 하려면 링크가 `/notifications/{id}` 로 가서 읽음 표시하고
302 로 진짜 목적지로 보낸다. 한 홉 늘지만 스크립트 없이 정확히 돌고, 가운데
클릭·새 탭도 그대로 산다.

**실시간은 v1 에서 하지 않는다.** 지금 실시간은 `work:{id}` 토픽이고 *「토픽 이름이
권한 경계이기도 하다」* 가 규약이다(`src/lib/realtime.ts`). `user:{id}` 는 **새 권한
경계를 하나 더 만드는 일**이라 `0012` 를 다시 짜야 한다. 반면 알림은 §4 에서
「사건」으로 정했으므로 **몇 초 늦어도 깨지는 것이 없다.** 급한 것(내 차례·지연)은
이미 화면에 붙어 있다.

## 9. 하지 않을 것

| | 왜 |
|---|---|
| **업무 없는 쪽지** | §5 의 `not null`. 여는 순간 메신저가 된다 |
| **그룹 쪽지·단톡** | 1:1 만. 여럿에게 물어야 하는 일이면 그건 **참여자로 부를 일**이다 |
| **알림 설정 화면**(갈래별 켜고 끄기) | 설정이 필요할 만큼 시끄러우면 §7 의 규칙 셋이 잘못된 것이다. **설정으로 덮지 않는다** |
| **이메일·푸시 알림** | 이 제품은 *「망분리 환경에서 외부 호출 0건」* 을 어렵게 사실로 만들었다(폰트까지 자체 호스팅, CSP 에서 CDN 제거). 메일 발송은 그것을 한 줄로 깬다 |
| **「업무에 옮기기」 단추** | §2. 누르라고 만들면 안 누른다 |

## 10. 시험 넷

이 저장소는 규칙을 **시험으로** 지킨다(`contrast` 38쌍 · `design-lint` 8검사 ·
`squint` 5화면). 새 규칙에도 자를 단다.

1. **`rls.test.mjs` 에 한 줄** — *쪽지를 받은 사람이 그 업무를 못 읽는다.*
   §3 의 결정을 **DB 가 증명**한다. 이것이 없으면 「안 보여준다」는 말일 뿐이다.
2. **`browser.test.mjs` 에 무JS 동선** — 스크립트를 끈 채 ⓐ `@` 없이 체크박스로
   사람을 부르고 ⓑ 종을 열고 ⓒ 눌러서 읽음 처리까지.
3. **소음 시험(새로)** — 시드에 하루치 활동을 넣고 **한 사람에게 쌓이는 알림 줄
   수**를 센다. 열 줄을 넘으면 실패. §7 의 「묶기」와 「내가 한 일 제외」가 조용히
   풀리면 여기서 잡힌다.
4. **`design-lint` 에 z-index** — 여섯 번째 층을 만든다면 `globals.css` 의 목록과
   실제 쓰임이 어긋나지 않는지. 지금 *「`z-[9999]` 0건」* 인 상태를 지킨다.

실눈 시험은 종에 안 걸린다 — `main` 만 흐리게 하고 머리 줄은 그 밖이다. 대신 §6 의
뒤집기 배지가 색 예산을 안 쓰므로 화면의 색 갈래는 그대로다.

## 11. 아직 안 정한 것

- **알림 드롭다운의 z 층.** 규약이 다섯(10·20·30·40·50)이고 여기 맞는 것이 없다.
  여섯 번째를 만들지, `z-10`(고정 헤더 안쪽)에 얹을지.
- **쪽지 읽음을 보낸 사람에게 보여줄지.** `read_at` 은 어차피 있다. 보여주면
  "다시 물어볼까"를 판단할 수 있지만, 공공 조직에서 「읽고 답 안 했다」가 보이는
  것은 예민하다.
- **알림 보관 기간.** `notification` 은 읽어도 안 지운다. 몇 달치가 쌓이면 정리
  기준이 필요하다(`activity` 는 감사 기록이라 영구가 맞지만 이쪽은 아니다).
- **쪽지함을 왼쪽 메뉴에 넣으면 「업무」 그룹이 다섯 개가 된다.** 지금 넷이다.
