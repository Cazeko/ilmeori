## 2. 문제 정의

### 2.1 4단 구조

**1단 — 분산**
같은 업무를 여러 부서·담당자가 함께 처리하지만, 자료는 각자의 PC와 개인 폴더에 있다. 협조하려면 파일을 메신저·전화·공문으로 주고받고, **어느 것이 최신본인지 아무도 확신하지 못한다.**
→ *과제 원문: "업무자료가 개인 단위로 관리되어"*

**2단 — 비가시성**
이 업무가 지금 어디까지 왔는지 팀이 모른다. 담당자에게 직접 물어야 알 수 있고, 담당자가 부재하면 확인할 방법이 없다.
→ *과제 원문: "공동작업에 한계", "실시간 공유 체계가 필요"*

**3단 — 제도는 열렸는데, 현장은 그대로**

> 여기가 v0.1에서 가장 크게 바뀐 부분이다. **"망분리 때문에 민간 협업도구를 못 쓴다"는 논거는 폐기했다.**

| 사실 | 신뢰도 |
|---|---|
| 망분리의 직접 근거였던 「국가 정보보안 기본지침」 **제40조가 2026년 5월 1일자로 삭제**됐다. 지침명도 「국가 사이버보안 기본지침」으로 바뀌고 N2SF(다층보안체계) 조항이 신설됐다 | **[확인]** |
| 국가정보원 스스로 *"전체 공공기관 중 망분리 적용은 11%"*, *"망분리가 신기술 발목을 잡는다는 건 다소 오해"*라고 공개 발언했다 | **[확인]** |
| CSAP(클라우드 보안인증)도 2026.4.20 국정원 단일 검증체계로 일원화가 공표돼 **2027년 7월 폐지·재편**된다 | **[확인]** |

즉 **논거를 특정 조문이나 인증제도에 걸면 발표 시점에 또 무너진다.** 3개월 전에 이미 한 번 무너졌다.

살아남는 축은 이것이다 — **제도와 현장의 실행 격차.**

- 2026년 KISA N2SF 도입지원 수요기관 6곳(기후에너지환경부·한전KDN, 성평등가족부, 우정사업본부, 한국도로공사, 한국부동산원, 한국연구재단)에 **광역·기초 지자체가 하나도 없다** **[확인]**
- 지자체 망분리 관련 국비 지원은 예산 확보에 실패했다 **[단일]**
- N2SF는 기관이 직접 C/S/O 등급분류와 예외 입증 부담을 져야 하는 구조라 **자동으로 열리지 않는다** **[확인]**

> **"지침은 바뀌었는데, 내 PC는 그대로입니다."**
> 이게 2026년 기초지자체의 현실이고, 일머리가 파고들 실제 틈이다.

**4단 — 그리고 이 취약함이 터지는 순간: 인사이동**
평소에도 업무가 개인에게 묶여 있으니, 담당자가 바뀌면 맥락이 통째로 사라진다. 남는 건 정리 안 된 파일 더미와 떠나기 직전에 기억으로 급조한 인계서 한 장이다.

### 2.2 인사이동이 실제로 얼마나 잦은가 **[확인]**

- 「지방공무원 임용령」 제27조가 **필수보직기간 2년**을 정하고 있다(실·국 내 유사직위 전보 등은 1년 이상, 경력경쟁임용자 3년)
- 그런데 제4항제6호(기관장이 특별히 인정하는 경우, 연간 전보인원 10% 이내)라는 예외가 광범위하게 쓰인다
- **강원도감사위원회 2025년 정선군 감사**: 전보 1,067명 중 **526명(약 49%)**이 이 예외로 필수보직기간 내 전보

### 2.3 그 결과가 얼마인가 **[확인]**

행정안전부 연구용역 — **한국행정연구원(2011) 「행정업무 효율성 진단 및 관리방안 구축: 업무 인계인수를 중심으로」**

> - 현행 인계인수가 **"효율적이다" 15.5%** vs **"비효율적이다" 35.0%**
> - 업무파악 기간 — 인계인수 **만족 시 2.64개월**, **불만족 시 3.78개월**
> - 그 **차이 1.14개월**. 3.78 대비 **30.2%**
> - **대면 인계인수는 길어야 반나절, 통상 30분 정도**에서 종료

> ⚠️ **1.14개월과 30.2%는 같은 사실의 두 표현이다(1.14 ÷ 3.78 = 30.16%). 곱하지 않는다.**
> 곱하면 손실을 두 번 센다. 예산을 다루는 사람은 검산한다.
> 안전한 문장: *"부실 인계 시 3.78개월, 충실히 인계하면 2.64개월 — **1.14개월(30.2%) 단축**입니다."*

→ 10장의 기대효과는 이 수치 위에 세운다. **추정치를 쓰지 않는다.**

**그리고 전자적 인계·인수는 이미 의무다 [확인].**

행정안전부 보도자료 「행정기관 업무 인계 인수 전자 방식으로 바꾼다」(2018.4.17., 심보균 차관)

> *"중앙부처 공무원 업무 인계·인수 실태조사('17.10.13~10.19.)를 실시한 결과
> **시스템 이용률이 5%**로 부진한 것으로 나타났다"*
> *"※ 대상자의 **95%가 서면 인계·인수(2,602건)**, 시스템 이용률 5%(121건)에 불과"*

같은 보도자료가 ①**2018년 5월부터 전자적 인계·인수 의무화** ②온나라 접근성 보완·절차
간소화 ③편람 지침 정비 ④**매년 기관별 추진실적 점검**을 함께 발표했다.

> **발표 문장.** *"2017년 행안부 실태조사에서 인계·인수 시스템 이용률은 5%였습니다.
> 2,723명 중 2,602명이 종이로 했습니다. 그래서 2018년 5월부터 전자 방식이 의무가
> 됐습니다. **8년이 지났습니다 — 지금은 몇 %입니까?**"*

> ⚠️ 단서 둘. **(1) 「2017년 조사」임을 반드시 밝힌다.** (2) '인수인계 활용률'이 아니라
> **'전자적 방식(시스템) 이용률'**이다.
> ❌ **"공무원 55%가 인수인계 부실로 혼란(권익위 2024)"은 원 출처 미확인이다. 쓰지 말 것.**

### 2.4 왜 이것이 공익 문제인가

담당자가 바뀌면 민원 처리가 지연되고, 작년의 시행착오를 올해 다시 반복한다.
**이건 공무원의 편의 문제가 아니라 행정 연속성의 문제이며, 곧 시민이 받는 서비스의 품질 문제다.**

## 3. 해결 방안

### 3.1 한 줄 정의

> 화성특례시 공무원이 **팀 단위로 업무를 쌓고**, 인사이동이 와도 그 일머리를 **끊김 없이 넘기는** 내부 협업 플랫폼.

### 3.2 설계 원리

> **평소 협업의 부산물이 곧 법정 문서가 된다.**

문서를 쓰기 위해 따로 무언가를 입력하게 하지 않는다. 평소 협업 기록(진행상태·대화·변경이력·문서·결재 의견)이 그대로 법정 서식의 각 항목에 대응하도록 구조를 설계했다.

**세 층으로 놓는다.**

```
[3층]  온나라 문서      별지 제1호서식 · 시행문 · GPKI · 공공기록물     ← 건드리지 않는다
          ↑ HWPX로 넘긴다
[2층]  일머리 — 문서    검토·협조  +  별지 제2호서식(보고서·계획서·검토서)
                        +  별지 제12호서식(업무인계·인수서)
          ↑ 근거 꼬리표
[1층]  일머리 — 기록    업무 · 문서 · 대화 · 쪽지 · 이력 · 실시간
```

1층이 쌓이면 2층이 저절로 쓰이고, 2층이 3층으로 넘어간다. **이 화살표 두 개가 제품의 전부다.**

### 3.3 비중

| 영역 | 비중 | 역할 |
|---|---|---|
| **부서 간 협업 (1층)** | 55% | 제품의 본체. 일상 사용은 전부 여기서 일어난다 |
| **결재·문서 (2층)** | 30% | 협업을 쓰게 만드는 이유. **이게 없으면 아예 안 쓴다** |
| **업무 인계·인수** | 15% | 협업이 축적되었을 때 발휘되는 결과. 차별화 지점 |

> 결재는 **입장권**이다 — 결재가 없으면 공무원은 이 화면을 애초에 열지 않고,
> 열지 않으면 1층에 아무것도 쌓이지 않는다. 자문의 첫 문장이 정확히 그것이었다.

> 인계·인수는 주인공이 아니라 **증거**다. *"협업 도구를 만들었더니 인계 문제까지 풀렸다"*가 *"인계 도구입니다"*보다 강하다.

## 4. 핵심 기능

### 4.1 과제 요구사항 매핑

| 과제 요구 | 구현 | 구현 상태 |
|---|---|---|
| 문서·업무 **공동편집** | 문서를 **섹션 단위로 분할 편집**. 편집 중 섹션은 잠기고 `○○○ 편집 중` 표시 | **완료·검증** |
| **진행상태 관리** | 상태(대기/진행중/검토/완료) + 지연 파생 + 칸반 보드 | **완료·검증** |
| **변경이력 기록** | 모든 사건을 **DB 트리거가 자동 기록**(append-only) | **완료·검증** |
| **접근권한 관리** | 역할(소유/편집/열람)을 **RLS로 DB가 강제** | **완료·검증** |
| **실시간 공유 체계** | 변경 즉시 반영 + 접속자 표시. 채널 권한도 **같은 RLS 함수**가 지킨다 | **완료·검증** |
| **팀 단위 협업** | 업무 보드 · 댓글 · 첨부파일 | **완료·검증** |
| **업무 인계·인수** | 담당 업무 일괄 이관 + **규칙 기반** 인계서 초안 생성 | **완료·검증** |

**v0.3에서 더한 것** — 과제 요구를 넘어, 현직 관리자 자문(11장)에서 *"이게 없으면 공무원은 아예 쓰지 않는다"*고 지목된 셋.

| 추가 기능 | 구현 | 근거 |
|---|---|---|
| **결재 — 「검토·협조」** | 결재유형 8가지(규정 제10조·시행규칙 제4조 낱말) · 조직도 기반 결재선 자동 생성 · 결재선 복사 | 4.5 |
| **온나라 연계** | 협의 끝난 문서를 **별지 제2호서식 HWPX**로 내보내 온나라 기안에 얹는다 | 4.5 |
| **쪽지** | 공공기관 고유의 비동기 메시지. 업무에 붙고 **읽은 시각이 증빙으로 남는다** | 4.6 |

### 4.2 화면 (8개)

| 화면 | 역할 |
|---|---|
| `/login` | 로그인 + **데모 계정 원클릭 진입** |
| `/` | 대시보드 — 내 업무 / 팀 현황 / 이번주 마감 / **"작년 이맘때"** 위젯 |
| `/works` | **업무 보드** — 칸반 ↔ 리스트 토글, 부서·담당자 필터 |
| `/works/[id]` | **업무 상세** — 탭 5개: `문서` `대화` `결재` `이력` `참여자·권한` |
| **`/approvals`** | **결재함** — `대기 / 예정 / 처리 / 완료 / 전체` + 최근·즐겨찾는 서식 |
| `/handover` | 인계·인수 — 대상 업무 선택 → 인수자 지정 → **규칙으로 인계서 초안 생성** → 이관 |
| `/audit` | 감사로그 — 열람·수정 기록 |
| **쪽지** | 화면이 아니라 **모든 화면 위의 층**. 상단 배지 + 업무 안에서 바로 보낸다 |

> **데모 계정 원클릭이 중요하다.** 심사위원이 웹앱 주소로 접속했는데 회원가입 화면이 뜨면 대부분 이탈한다. 로그인 화면에 `[김○○ 주무관으로 보기]` `[박○○ 팀장으로 보기]` 버튼을 두어 **권한 차이까지 직접 체험**하게 한다.

### 4.3 「업무인계·인수서」 자동 작성 — **모델 없이**

**법정 근거 [확인]**
- 법정 명칭은 '사무인계인수'가 아니라 **「업무의 인계·인수」**
- 근거: **「행정업무의 운영 및 혁신에 관한 규정」 제61조**, 같은 규정 **시행규칙 제45조**
- 서식: **시행규칙 별지 제12호서식 「업무인계·인수서」**

**실제 서식 구조와 우리 데이터의 대응**

| 법정 서식 항목 | 일머리에 이미 쌓여 있는 것 |
|---|---|
| 1-가. 담당 업무 | `work` 중 내가 소유자인 업무 목록 |
| 1-나. 주요 업무계획 및 진행사항 | `work.status` + `activity` 타임라인 |
| 1-다. 현안사항 및 문제점 | `comment` 중 미해결 논의 |
| 1-라. 주요 미결사항 | 기한 초과·검토 단계에 멈춘 업무 |
| 2. 관련 문서 현황 | `document` · `attachment` |
| 3. 주요 물품 및 예산 등 | (수기 입력 필요) |
| 4. 그 밖의 참고사항 | `work.previous_year_work_id` 연결 이력 |

> 통념과 달리 **'유의사항'이라는 항목은 실제 서식에 없다.** 이런 디테일이 틀리면 공무원 심사위원이 즉시 알아본다.

**조립뿐이다. 그리고 조립에는 모델이 필요 없다.** 없는 내용을 만들지 않는다. 축적된 협업 이력을 법정 서식에 배치한다.
출력 3종: ① 인계·인수서 초안 ② 미결사항 자동 추출 ③ 인수자용 3줄 브리핑

**고르는 것은 규칙표(정규식) 5갈래다** — 기한 · 질문 · 결정 대기 · 이견 · 약속
(`src/lib/handover-draft.ts`). 걸린 문장은 **원문 그대로** 칸에 옮기고 요약하지 않는다.
그래서 문장마다 「어느 기록에서 나왔는가」를 붙일 수 있다. 모델이 고르면 왜 골랐는지를
문서에 적을 수 없고, 그러면 근거 꼬리표가 아무것도 보증하지 못한다.

> 억지로 끼워넣은 AI가 아니다. **애초에 모델을 부르지 않는다.**
> 규칙은 **놓치고**(빈칸), 모델은 **지어낸다**(거짓말). 놓친 건 셀 수 있고 지어낸 건 셀 수 없다.

**그리고 같은 엔진이 서식 하나를 더 뽑는다.** 인계서를 조립하는 규칙은 「기록의 어느 조각이 서식의 어느 칸에 들어가는가」다. 그 대응표만 바꾸면 **별지 제2호서식(보고서·계획서·검토서)**이 나온다 (4.5).

| | 별지 제12호서식 | **별지 제2호서식** |
|---|---|---|
| 언제 | 인사이동 때 | **평소, 결재 올릴 때마다** |
| 빈도 | 연 1~2회 | **주 단위** |
| 상태 | 구현 완료 | v0.3 신규 |

> 빈도가 이 제품의 사용률을 결정한다. 인계서만으로는 1년에 한 번 열리는 도구가 되지만,
> **기안 초안까지 뽑으면 매주 열린다.**

**AI 존재감은 채팅창으로 만들지 않는다.** 하이웍스가 문서 제목 옆에 「✦ 요약」 버튼을 붙인 방식을 따른다 — AI는 **산출물이 나오는 자리에 버튼으로** 있고, 결과에는 언제나 *"이 문단은 어느 기록에서 나왔는지"* 근거 꼬리표가 붙는다. 화성시가 이미 HAI-MATE를 운영 중인 상황에서 범용 AI 채팅창을 세우는 것은 5.1의 논거를 스스로 무너뜨리는 일이다.

### 4.4 연간 주기 소환

공무원 업무는 연 단위로 반복된다(예산편성·정기행사·점검·정산). 실질적인 인계는 **"작년 담당자가 이맘때 무엇을 어떻게 했는가"**다.
`work.previous_year_work_id`로 작년 같은 업무를 연결하고, 대시보드에서 "작년 이맘때" 위젯으로 소환한다.

### 4.5 결재 — 「검토·협조」와 온나라 연계

> 현직 관리자 자문에서 나온 첫 문장은 이랬다.
> *"잔디·네이버웍스 이런 거 기본으로 깔린 게 결재 시스템이다. **이거 없으면 아예 쓸 이유 자체가 없다.**"*
> 그리고 이유는 편의가 아니라 증빙이었다 — *"그때 저거 님이 결재해주셨는데 이제 와서 왜 딴소리."*

**그런데 공무원의 결재를 그대로 만들면 온나라와 정면충돌한다.** 온나라 문서시스템은 중앙부처·자치단체 전 공무원이 쓰는 법정 전자결재시스템이고, 전결·대결·순차협조·병렬협조가 이미 다 있다. 여기에 GPKI 행정전자서명과 공공기록물 등록이 붙는다. *"그거 온나라에 있는데요, 법적 효력은요?"* 한 마디에 무너진다.

#### 법령이 자리를 나눠 준다 **[확인]**

「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 **제3조**

> ① 기안문은 **별지 제1호서식**이나 **별지 제2호서식**에 따라 작성한다.
> ③ 별지 제2호서식과 별지 제4호서식은 **보고서, 계획서, 검토서 등 발신할 필요가 없는 내부결재문서에만 사용한다.**

| 서식 | 문서 | 지금 어디서 만드나 |
|---|---|---|
| 별지 **제1호**서식 | 공문·시행문 (발신 O) | **온나라 문서** — 건드리지 않는다 |
| 별지 **제2호**서식 | **보고서·계획서·검토서 (발신 X)** | 온나라 문서관리카드로 결재는 한다. **본문은 사람이 쓴다** ← 일머리가 초안을 만든다 |
| 별지 **제12호**서식 | 업무인계·인수서 | 일머리 (구현 완료) |

같은 규정, 같은 규칙, 다른 별지다. 인계서를 뽑는 엔진과 **같은 엔진**으로 보고서·계획서를 뽑는다.

#### (1) 자체 결재 — 「검토·협조」

결재유형 **8가지**를 규정의 낱말 그대로 쓴다 — 「행정업무의 운영 및 혁신에 관한 규정」
**제10조**(결재·전결·대결)와 시행규칙 **제4조**(검토·협조).
`기안` · `결재` · `최종결재` · `전결` · `대결` · `순차협조` · `병렬협조` · `사후보고`

> ⚠️ **「법정 8종」이라고 부르지 않는다.** 온나라 고시(행안부 제2024-28호)가 세는 8종은
> `기안·검토·협조·병렬협조·결재·전결·대결·전대결`이라 **목록이 같지 않다** — 거기에는
> 「검토」·「전대결(위임전결사항의 대결)」이 있고 여기에는 「최종결재」·「사후보고」가 있다.
> 「법정」이라는 강한 수식어를 붙이면 목록이 다른 순간 정확성으로 승부하는 제품의
> 정체성이 흔들린다. **enum 은 고치지 않는다** — 마이그레이션과 RLS 시험이 딸려 온다.

| 자문에서 나온 요구 | 구현 |
|---|---|
| *"조직도가 있어야 결재라인"* | `profile.rank`(직급 서열) 신설 → 상위자 자동 추적 |
| *"바빠 죽겠으니 빠바바밥 해야 하고"* | 서식을 고르면 **결재선 자동 생성**(기안→팀장→과장→국장 전결) |
| *"남이 결재한 거 그대로 쓰기 기능, 무조건 있어야"* | **결재선 복사** — 다른 문서·부서의 결재선을 불러온다 |
| *"다 저게 증빙"* | 결재란 서명 + 시각 + append-only 이력 + 열람로그 |

화면은 공무원이 이미 아는 모양을 따른다 — 조직도에서 골라 결재선에 넣고 ▲▼로 순서를 바꾼다. 결재란은 행이 `결재`/`협조`, 열이 직위인 격자이고, 전결권자 칸에는 「전결」이 찍힌다. 진행 정도는 `3/5` 한 칸으로 보인다. 문서번호는 `HS-협조-20260808-0001` 꼴이다.

> **무엇을 하지 않는가 — 최종 결재권자의 서명은 우리가 받지 않는다.**
> 시행규칙 제4조제6항이 정한 결문의 구성은 *"기안자·검토자·**협조자**·결재권자의 직위나 직급 및 서명"*이다.
> 우리는 앞의 셋을 맡고, 마지막 하나는 온나라에 남긴다. 그 선을 넘지 않는 것이 이 설계의 힘이다.

#### (2) 왜 그 앞단이 비어 있는가 **[확인]**

규정은 이견을 남기라고 한다.

> 기안문을 검토 또는 협조할 때 내용과 다른 의견이 있으면 해당 문서 또는 별지에 그 의견을 표시하여, 결재권자가 결재할 때 또는 향후 그 업무 담당자가 참고하도록 하여야 한다.
> 총괄책임자는 검토자란에 서명하되, 다른 의견이 있으면 직급 다음에 **"(의견 있음)"**이라고 표시한다.

그런데 실무의 협조 절차는 *"협조 전에 실무자에게 **미리 연락**"*으로 시작한다. 그 "미리 연락"이 카톡·전화·대면이다. **이견은 거기서 소거되고, 온나라 결재란에는 전원 서명이라는 결과만 남는다.** 누가 언제 무엇을 걱정했는지는 사라진다. 담당자가 바뀌면 처음부터 다시 협의하고, 감사가 나오면 답할 수 없다.

> *"저희는 결재를 대체하지 않습니다. 결재란에 서명이 찍히기 **전**에 무슨 일이 있었는지를 남깁니다. 그리고 그 기록으로 기안문을 씁니다."*

#### (3) 연계 — 온나라 기안 원문 내보내기

```
 일머리에서 협의·검토   →   근거 꼬리표가 붙은 초안      →   별지 제2호서식 HWPX   →   온나라 기안
 (쪽지·대화·이력 축적)      "이 문단은 3/12 김주무관        (한/글에서 그대로 열림)     (법적 효력)
                             쪽지에서 나왔습니다"
```

- HWPX는 **ZIP + XML(OWPML) 개방 포맷**이다. 한/글로 만든 **템플릿을 열어 본문 XML만 치환**하고 다시 압축한다. 서식·표·머리글이 보존되고, **열리는 것이 템플릿으로 보장된다**
- PDF가 아니라 **HWP 계열**이어야 하는 이유는 하나다. 결재에 올리려면 고쳐 쓸 수 있어야 한다
- 선례가 있다 — 네이버웍스는 **결재 API 연동**으로 *"외부 솔루션에서 작성한 결재 문서까지 자연스럽게 연결"*한다. 우리는 API 없이 파일로 하므로 실현 문턱이 더 낮다

### 4.6 쪽지 — 공무원의 메신저는 카톡이 아니다

메신저를 붙이되 **카톡형 실시간 채팅을 만들지 않는다.** 근거는 경쟁 제품 쪽에 있다.

삼성SDS 브리티웍스 **공공**은 대표 기능 8개 중 하나로 **「쪽지」를 독립 배치**하고 이렇게 쓴다.

> *"공공기관에서 오랫동안 사용해온 **쪽지 방식을 그대로 유지**하면서, 편의 기능과 화면 디자인을 새롭게 개선했습니다."*

민간용 메신저를 다 갖춘 회사가 공공 제품에서 굳이 쪽지를 남긴 것은, 그것이 공공의 실제 문법이기 때문이다.

| | 카톡형 채팅 | **쪽지** |
|---|---|---|
| 공무원 익숙도 | 개인용으로만 | **업무용 표준** |
| 자바스크립트 없이 | ❌ 불가 | ✅ 폼 제출로 동작 |
| 기록성 | 흘러간다 | **읽은 시각이 증빙** |
| 카톡과의 경쟁 | 못 이긴다 | 경쟁하지 않는다 |

**쪽지는 업무에 붙는다.** 업무 카드에서 바로 보내고, 받는 사람 화면에 실시간 배지가 뜨고(6.4의 신호 층을 그대로 쓴다), 읽으면 그 시각이 이력에 박힌다. 그리고 **그 쪽지가 인계서와 기안 초안의 근거로 인용된다.** 카톡은 증빙이 되지 않지만 이 쪽지는 append-only 기록이다.

## 5. 경쟁 지형과 차별성

> v0.1에서 가장 많이 바뀐 장이다. 조사 결과 **경쟁자가 셋 더 있었다.**

### 5.1 화성특례시 `HAI-MATE` — 이미 돌아가고 있다 **[확인]**

화성특례시는 **2026년 2월부터 전 직원 대상 AI 행정비서 HAI-MATE를 정식 운영 중**이다. 기능은 문서 초안 작성·검토, 회의자료·보고서 요약, 정책·행정 자료 검색, 멀티 LLM 비교.

**이걸 모르고 발표하면 한 방에 끝난다.** 먼저 언급하고 관계를 정의해야 한다.

> *"화성시는 이미 HAI-MATE로 개인 업무를 돕고 있습니다. 그런데 그 결과물은 여전히 개인 PC에 남습니다.
> HAI-MATE는 **개인의 생산성** 도구이고, 일머리는 **팀의 기억** 구조물입니다. 대체가 아니라 위층입니다."*

### 5.2 온나라 — 협업도 인계인수도 **이미 제도상 존재한다** **[확인]**

- '온나라 서비스'는 '온나라 문서'(전자결재) 외에 **「온나라 이음」**(구 나라e음, 2014~)이라는 협업시스템을 포함한다
- **대통령령 제46조의2**가 이를 *"실시간 의사소통이 가능하고 공동작업 및 실적관리가 필요한 업무를 등록·관리"*하는 것으로 규정한다
- 「행정기관의 업무관리시스템 규격」(**행정안전부 고시 제2024-28호**, 2024.4.15.) **제8장 전체가 「인계인수 기능」**이다. *"전임자와 후임자간 전자적으로 인계인수 할 수 있는 기능"*으로 정의하고, 인계자·인수자·입회자·검토자 구분 등록과 **인수요청 → 인수확인 → 입회확인** 워크플로까지 규정한다. 하위 항목도 담당업무·예산·물품·주요 업무계획 및 진행사항·과제카드·주요 실적·현안사항·미결사항·참고 의견으로 **별지 제12호서식과 같은 뼈대**이고, 나항이 *"업무인계·인수서는 …「별지 제12호서식」을 적용할 수 있다"*고 직접 지목한다. 목차상 **「(선택)」 표기가 없다** = 표준 필수 장

따라서 **"온나라에 협업 기능이 없다"도, "인계인수 기능이 없다"도 말하면 안 된다.**
둘 다 있다. 살아남는 논거는 다섯이다.

1. 온나라 이음의 협업은 **기관 간 지식교류·포인트·영상회의** 수준이지, 부서 단위 실무 협업(자료 공동편집·진행상황 추적)이 아니다
2. '온나라 문서'는 **결재문서 중심**이라 다양한 유형의 기록을 포괄하지 못한다 — 황진현·임진희(2023) **[확인]**
3. 우리는 **결재 이전 단계**를 다룬다. 지금 그 단계는 개인 PC와 메신저에 있다
4. **인계인수 — 칸은 있는데 채우는 방법이 없다.** 고시 제8장 전문에 **'자동생성'·'초안'·'추출'이 한 번도 나오지 않는다.** 조문은 전부 「~을 등록할 수 있는 기능을 제공」 형태다. 『2025 행정업무운영 편람』 257쪽 각주가 스스로 적는다 — *"※ **대부분 서식에 글자(텍스트 형식)로 입력하며**, 과제카드 및 주요실적의 경우 해당 카드 및 전자문서, 메모보고 등을 선택하여 등록함."* **[확인]**
5. **내부결재문서 — 온나라도 결재는 하지만 본문은 사람이 쓴다.** 시행규칙 제3조제3항이 별지 제1호(발신)와 제2호(내부결재)를 나눠 두었지만, 온나라 **문서관리카드**는 둘 다 다룬다. 우리 자리는 그 본문을 **협업 기록에서 초안으로 만들어 온나라 기안에 얹는 것**이다 (4.5)

> **이 한 줄로 통일한다.**
>
> *"온나라에 인계인수 서식은 이미 있습니다. 고시 제2024-28호 제8장이고 별지 제12호서식까지
> 지목합니다. 저희가 만든 건 서식이 아니라 **그 칸을 원문 기록에서 채우는 규칙**입니다."*

> ⚠️ **두 가지를 조심한다.**
>
> **(1)** 편람 각주의 뒷부분(「과제카드·전자문서·메모보고를 **선택하여 등록**」)을 빼고 인용하면 안 된다.
> **온나라도 일부는 골라 담는다. 「100% 타이핑」이라고 말하지 말 것.** 안전한 선은 **단위의 차이**다 —
> *"온나라가 골라 주는 것은 **카드와 문서 단위**입니다. **문장 단위**로 어느 대화에서 나왔는지까지는 가지 않습니다."*
>
> **(2)** 「내부결재문서 자리에는 시스템이 없다」고 말하면 안 된다. 온나라를 매일 쓰는
> 심사위원에게는 **첫 문장에서 끝난다.**

> 3~5번이 v0.3에서 화면으로 구현됐다. v0.2까지는 문장으로만 주장하고 화면에는 없었다.

### 5.3 행안부 「온AI」 — 중앙부처엔 이미 왔고, 지자체엔 2027년 이후에 온다 **[확인]**

행정안전부가 온나라를 **대체**하는 「지능형 업무관리 플랫폼」의 서비스명이 **「온AI」**다. 2026년 2차 사업 **183억 1,300만원**을 삼성SDS 컨소시엄(솔리데오시스템즈·유알피·네이버클라우드)이 수주했다.

- **2026-04-30 정식 오픈** — 삼성SDS **브리티웍스**가 온AI 공식 협업솔루션으로 선정돼 기획예산처 등에서 가동 중. 모바일 공무원증 인증·화면 캡처 방지·양자내성암호(PQC)
- 2026년: 전 중앙부처 확대
- **2027년 이후: 전국 지자체 순차 확산**

> v0.2에서 *"2027년에 온다"*고 쓴 것은 절반만 맞았다. **중앙부처엔 이미 왔다.** 그래서 문장을 바꾼다 —
> *"범정부 플랫폼은 이미 중앙부처에서 돌고 있습니다. 다만 **기초지자체 도착은 2027년 이후**입니다. 그 1~2년의 공백에서 축적되지 않은 업무 기억은 영구히 사라집니다."*
>
> 이 정직함이 오히려 **"우리는 우리 제품의 수명까지 계산했다"**는 신호가 된다.

**정직하게 말하는 것이 유일한 답이다.**

> *"범정부 플랫폼이 옵니다. 다만 지자체 도착은 2027년 이후입니다.
> 그때까지 기초지자체에는 공백이 있고, 그 공백에서 축적되지 않은 업무 기억은 영구히 사라집니다.
> 그리고 일머리가 축적한 데이터 구조는 그 플랫폼으로 이관 가능하도록 설계했습니다."*

이건 약점이 아니라 **"우리는 우리 제품의 수명까지 계산했다"**는 신호다.

### 5.4 민간 협업툴 — 5개 제품 직접 조사 **[확인]**

제품 페이지와 실제 화면을 직접 뜯어보고 정리했다. 결론부터: **결재는 다섯 곳 모두 있다. 그러나 다섯 곳 모두 「기업의 결재」이지 「행정의 기안」이 아니다.**

| 제품 | 결재 | 가져올 것 | 우리와 겹치지 않는 지점 |
|---|---|---|---|
| **브리티웍스 공공**(삼성SDS) | ✅ **브리티 메일 안에 통합** | **쪽지를 독립 기능으로 유지**한 판단 · *"기존 업무 방식은 그대로 유지하면서"* | 온AI의 협업 층. **별지 서식을 모른다** |
| **네이버웍스** | ✅ 결재선 요약(결재/합의 × 일반/병렬/순차) · 결재선 예외(생략·변경·참조) · **결재 API 연동** | 결재함 IA(`대기/예정/처리/완료/전체`) · **최근·즐겨찾는 서식** | 범용. 온AI 컨소시엄 소속이라 **닮을수록 손해** |
| **하이웍스** | ✅ **업무협조전** · 문서번호 `GA-협조-…` · 보존연한·보안등급 | 문서번호 체계 · 결재란 격자 · **제목 옆 「✦요약」 AI 버튼** | 중소기업용. 법정 서식 아님 |
| **flex** | ✅ 병렬/순차 · 전결 라벨 · 커스텀 양식 | **「진행 중 3/5」 진행률 배지** · 필터 칩 + 보기 저장 | *"전자결재보다 쉽고 메신저보다 체계적"* — 포지션은 같으나 대상이 사기업 |
| **지라** | ❌ | — | 자문 그대로 — *"그건 그냥 노션 쓰지, 지라 쓰지에서 끝난다"* |

**따라서 차별점은 「결재가 있다/없다」가 아니다.**

1. 다섯 제품 모두 **양식을 사용자가 만들게** 한다. 우리는 **법정 서식(별지 제2호·제12호)을 처음부터 알고 있다**
2. 다섯 제품 모두 **빈 양식에서 시작**한다. 우리는 **쌓인 협업 기록에서 초안이 채워져 나온다** — 근거 꼬리표까지 달고
3. 다섯 제품 모두 **PDF/자체 포맷**으로 내보낸다. 우리는 **HWPX**로 내보내 온나라 기안에 그대로 얹는다

> 네이버웍스가 「결재 API 연동」으로 외부 결재 문서를 끌어오는 것은 우리에게 **경쟁이 아니라 선례**다.
> 외부 시스템과 결재를 잇는 일이 이미 상용 제품에서 돌아간다는 뜻이므로, 실현가능성 질문의 답이 된다.

## 6. 시스템 설계

### 6.1 기술 스택

| 층 | 선택 |
|---|---|
| 프론트/서버 | **Next.js 16.3** (App Router) · React 19.2 · TypeScript |
| 데이터 | **Supabase** — Auth / Postgres + RLS / Realtime / Storage |
| 스타일 | Tailwind CSS v4 + **KRDS 토큰 + 화성특례시 BI** |
| 근거 선별 | **규칙표(정규식) 기반.** 인계서·기안 초안을 **모델 없이** 만든다 — LLM SDK 0개 |
| **문서 생성** | **HWPX** — 한/글 템플릿 + JSZip 본문 XML 치환 (별지 제2호·제12호서식) |
| **설치** | **PWA** — 네이티브 앱으로 가지 않는다. 아래 참조 |
| 배포 | Vercel |

> **왜 네이티브 앱이 아닌가.** 벤치마킹한 다섯 제품이 모두 앱을 낸다. 그래도 웹으로 간다.
> ① 공모전 제출물이 **「웹앱 주소」**다. 심사위원에게 설치를 요구하는 순간 이탈한다
> ② 로드맵이 **내부 업무망 온프레미스**(7.5)인데, 앱스토어 앱은 망분리 환경에 배포할 수 없다
> ③ 행안부가 만드는 온AI도 *"온나라를 대체하는 **웹 기반** 업무 환경"*이다
> ④ **자바스크립트 없이 도는 화면**이라는 이 제품의 전제를 PWA는 깨지 않는다 (실시간과 같은 덧붙이는 층)
> ⑤ manifest + service worker + 아이콘이면 반나절. 네이티브는 최소 2주
>
> 얻는 것은 홈 화면 아이콘·주소창 없는 전체화면·푸시 알림이다. **시연영상에서 폰 홈 화면 아이콘을 눌러 실행**하면 "앱"이라는 인상은 그것으로 완성된다.

| **`approval`** | 결재 문서 — 서식 종류·문서번호·보존연한·보안등급·상태(기안/진행/완결/반려/회수) |
| **`approval_step`** | 결재선 한 칸 — 순서·직위·**결재유형 8종**·서명 시각·의견(「의견 있음」) |
| **`memo`** | 쪽지 — 보낸이·받는이(다수)·업무 연결·본문 |
| **`memo_read`** | **읽은 시각** — 이것이 증빙이 된다 |

`profile`에 **`rank`(직급 서열)** 한 칸을 더한다. 결재선 자동 생성이 이 한 칸에서 나온다.

### 6.3 아키텍처

```
Next.js 16 (App Router)  ──►  Supabase
  · 화면 + Server Actions          · Auth
  · proxy.ts (세션·CSP·인증게이트)  · Postgres + RLS  ← 권한을 DB가 강제
  · /api/handover (규칙 기반)      · Realtime        ← 실시간 공유
                                   · Storage (private)

  ※ 바깥으로 나가는 화살표가 없다. **LLM 호출 없음** — 의존성 495개 중
     LLM SDK 0개, src/ 안에 외부 fetch 0회, 환경변수 4개(전부 Supabase)
```

### 6.4 실시간을 어떻게 붙였나

진정한 동시 편집(CRDT)은 13일 일정에서 위험이 크다. 대신 **잠금 + 즉시 반영**으로 갔다.
문서를 섹션 단위로 나누고, 편집 중 섹션은 DB가 잠근다(5분 만료). 충돌이 원천적으로 없어
시연이 안 깨진다. 그 위에 실시간을 얹었다.

**신호는 화면을 그리지 않는다.** 웹소켓으로 오는 것은 "이 업무에서 무언가 바뀌었다"는
한 줄뿐이다 — `{kind, work_id, actor, at}`. 제목도 본문도 파일 이름도 실려 오지 않는다.
그 한 줄을 받으면 브라우저는 **서버에 다시 묻고**, 화면에 나타나는 것은 언제나 RLS를
통과한 데이터다. 지연 판정·잠금 만료 같은 파생 상태도 서버 시계로 계산된 값 그대로다.

```
DB 트리거 ──► realtime.send ──► 토픽 work:<업무 id> ──► 브라우저 ──► router.refresh()
  (변경한 표에서)   신호만          RLS가 지키는 채널        구독              ▲
                                                                     서버가 다시 그린다
```

이렇게 한 이유는 broadcast의 권한 판정이 **채널에 들어올 때 한 번**이기 때문이다.
행 단위 필터가 없어서, 페이로드에 실은 것은 그 채널의 모두에게 그대로 간다.
Supabase가 제공하는 `realtime.broadcast_changes()`는 바뀐 행 전체를 싣는다 — 그래서 쓰지 않았다.

**토픽 이름이 곧 권한 경계다.** `realtime.messages`의 정책이 `app.can_read_work()`를 부른다.
업무 화면을 여는 판정과 **같은 함수**다. 업무를 볼 수 없는 사람은 웹소켓으로도 그 업무의
신호를 받지 못하고, 접속자 목록에도 들어오지 못한다(98개 시험 중 [13]이 이걸 확인한다).

**신호를 보내는 곳도 DB다.** 서버 액션 27개에 한 줄씩 넣는 대신 표에 트리거를 달았다.
이력을 트리거가 남기는 것과 같은 이유다 — 개발자가 빠뜨릴 수 없고, 앱을 거치지 않은
변경도 새어 나가지 않는다. 이력에 남지 않는 변경(항목 잠금)까지 신호가 나가는 것도
이 방식이라야 가능하다. 「○○○ 편집 중」이 상대 화면에 곧바로 뜨는 것이 그래서 된다.

**스크립트가 없으면 이 층은 아예 나타나지 않는다.** 이 제품의 화면은 자바스크립트 없이
전부 도는 것이 전제이고, 실시간은 원리상 그럴 수 없다. 그래서 덧붙이는 층으로만 만들었다 —
스크립트가 없으면 상자가 그려지지 않고, 나머지 화면은 지금까지와 똑같이 동작한다.
자바스크립트를 끈 브라우저 시험이 그것을 확인한다.

**편집 중인 사람의 화면은 가로채지 않는다.** 문서 항목을 쓰고 있는데 남의 변경으로 화면이
갈아 끼워지면 쓰던 글이 위태롭다. 그때는 "다른 사람이 대화를 고쳤습니다"라고 알리기만 하고,
반영할지는 그 사람이 정한다.

> **접속자 표시만은 DB가 보증하지 못한다.** 누가 접속했다는 사실은 각자의 브라우저가
> 알리는 것이라 원리상 위조할 수 있다. 그래서 **이름은 서버가 준 참여자 목록에서만 찾고**,
> 목록에 없는 사람은 수로만 센다. 채널에 들어온 것 자체는 RLS가 판정한 결과다.

- **2차예선 이후** — 여력이 있으면 Tiptap + Yjs로 동시 타이핑까지 확장

## 7. 보안

**시제품에는 실제 공문서를 단 한 건도 넣지 않는다.** 배포본의 모든 데이터는 가상이다. 발표에서 이 사실을 먼저 밝힌다.

| | 층 1: 시제품 | 층 2: 실제 도입 설계 |
|---|---|---|
| 환경 | 공개 인터넷 (Vercel + Supabase) | 내부 업무망 온프레미스 |
| 데이터 | **100% 가상 데이터** | 실제 공문서 |
| 목적 | 작동 증명 | 행정 적용 가능성 증명 |

### 7.1 구현 완료 · 검증 완료

| 항목 | 내용 |
|---|---|
| 인가 | 모든 테이블 RLS `default deny` + `force row level security` |
| 이중 방어 | 테이블 권한(GRANT) + 행 권한(RLS). `activity`엔 INSERT 권한 자체를 부여하지 않음 |
| 이력 무결성 | UPDATE/DELETE 정책이 **존재하지 않는** append-only. `SECURITY DEFINER` 트리거만 기록 |
| 권한상승 차단 | 소속·직급·계정상태를 본인이 변경 불가 (부서 변경을 통한 열람 확대 차단) |
| IDOR 차단 | URL에 UUID가 노출돼도 RLS가 차단 |
| 첨부파일 | private 버킷 + 단기 만료 signed URL. 공개 URL 부존재 |
| 인계 원자성 | `execute_handover()`가 권한 재확인 + 재실행 방지 + 원자적 이관 |
| 세션 | `SameSite=Lax` 쿠키(브라우저가 실시간 채널에 붙을 때 자기 토큰을 읽어야 해 `httpOnly`가 아니다 — 그 대비는 nonce 기반 CSP다). 토큰 **서명을 서버에서 검증**한다(ES256 + JWKS 로컬 검증, 만료 포함). 쿠키를 그대로 믿지 않는다. 다만 Auth 서버에 매 요청 묻지는 않으므로 **폐기된 세션은 토큰 만료까지 통과할 수 있다** — 그 뒤를 `profile.is_active` 확인과 RLS가 받친다. 왕복을 요청마다 없애기 위한 맞바꿈이고, JWT 수명을 줄이면 창이 그만큼 좁아진다 |
| 헤더 | nonce 기반 CSP · HSTS · `X-Frame-Options: DENY` · nosniff · Permissions-Policy |
| 키 관리 | `service_role` 키를 **애플리케이션에서 사용하지 않음**. `.gitignore` 선행 + 시크릿 스캔 |

### 7.2 검증 — 98개 행동 테스트

정책이 *존재하는 것*과 *실제로 막는 것*은 다르다. 실제 Postgres(PGlite)에 사용자를 흉내 내어 접속하는 테스트를 짰다.

```
npm run db:test

[1] 열람 권한 — 참여자가 아니면 볼 수 없다
[2] IDOR — UUID를 알아도 뚫리지 않는다
[3] 역할 — 열람자는 고칠 수 없다
[4] 이력 위조 — 감사 기록은 손댈 수 없다
[5] 권한 상승 — 소속을 바꿔 남의 부서를 엿볼 수 없다
[6] 섹션 편집 잠금 — DB가 강제한다
[7] 주인 없는 업무 방지 — 그리고 업무 자체는 지워진다
[8] 공개 범위 — 편집 권한과 권한 배분 권한은 다르다
[9] 인수인계 — 제품의 클라이맥스
[10] 열람 로그 — 누가 봤는지 남는다
[11] GRANT 층 — RLS가 아니라 권한에서 막히는가
[12] 익명 접근
[13] 실시간 — 신호는 나가는가, 그리고 아무에게나 가지는 않는가
[14] 열람기록 — 화면이 다시 그려질 때마다 쌓이지 않는가

98개 통과 · 0개 실패
```

> [13]의 28개는 PGlite 위에서 돈다. 웹소켓 참가 판정과 토큰 전달은 그 안에 없으므로
> `npm run db:realtime`(실제 프로젝트, 12건)과 `npm run test:realtime`(창 두 개, 11건)이
> 그 층을 따로 확인한다. 실제로 그 둘만 잡아낸 것이 있다 — 배달되는 페이로드에는 서버가
> 붙이는 메시지 uuid 가 한 칸 더 들어 있는데, PGlite 스텁은 그 층을 재현하지 못한다.

> 이 테스트가 통과한다는 것은 **애플리케이션 코드에 버그가 있어도 권한 없는 사용자에게 데이터가 나가지 않는다**는 뜻이다.

### 7.3 2차예선 구현 예정

MFA(TOTP) · 로그인 rate limiting · 공무원 메일 도메인 화이트리스트 · 열람로그 UI · 개인정보 패턴 마스킹

(Pretendard 자체 호스팅은 완료했다 — `public/fonts/`, 외부 CDN 호출 0건)

### 7.4 모델 구간 — **비어 있다** [확인]

- **어떤 모델도 호출하지 않는다.** 의존성 495개 중 LLM SDK **0개**, `src/` 안에 외부 `fetch` **0회**, 환경변수 **4개**(전부 Supabase). 확인 명령이 그대로 증거다
- 그래서 **프롬프트 인젝션 표면이 없고, 전송 전 개인정보 마스킹이 필요한 구간도 없다.** 원문이 밖으로 나가지 않으므로 막을 것이 아니라 **애초에 없는 것**이다
- 근거 선별은 **규칙표(정규식) 5갈래**가 한다 — 기한·질문·결정 대기·이견·약속. 고른 문장은 **원문 그대로** 서식 칸에 옮기고, 요약하지 않는다
- **실패 방식이 다르다.** 규칙은 **놓치고**(빈칸), 모델은 **지어낸다**(거짓말). 놓친 건 셀 수 있고 지어낸 건 셀 수 없다

> ⚠️ 오랫동안 이 절은 「AI 호출을 인터페이스로 추상화해 내부망 sLLM으로 모델만 교체」라고
> 적혀 있었다. **그런 인터페이스는 코드에 없다.** 2차 발표에서 「어떤 모델도 호출하지
> 않습니다」라고 말했고 제출물에 저장소 주소가 들어간다 — 두 말이 다르면 그 자리에서 끝난다.

> ⚠️ CSAP는 **2027년 7월 폐지·재편** 예정이므로 로드맵의 축으로 삼지 않는다 **[확인]**.

## 8. 디자인 시스템

### 8.1 원칙

> 실제로 시청에 도입되어도 이상하지 않으면서, 기존 관공서 시스템보다 명확히 잘 만들어진 것.

화려함이 아니라 **밀도와 일관성**으로 완성도를 만든다.

### 8.2 KRDS에 대한 입장

「디지털 정부서비스 UI/UX 가이드라인」과 KRDS는 **법령이 아닌 권고**이며 1차 적용 대상은 대국민 서비스다. 우리는 로그인 기반 내부 업무 시스템이므로 전면 준수 대상이 아니고, 대국민 사이트 구조를 그대로 적용하면 업무 도구로서 오히려 나빠진다.

체크리스트 자체가 `E(예외)` `N/A(해당없음)` 판정 칸을 둔다. 그래서 **취사선택하고 판단 근거를 문서화**한다.

> 발표 입장: *"준수했습니다"가 아니라 **"검토하고 취사선택했습니다"**.*

| 층 | 선택 | 이유 |
|---|---|---|
| 디자인 토큰 | KRDS 값 채택 | 비용 없이 "정부 서비스다운" 인상 |
| 컴포넌트 구현 | 브라우저 기본 요소 + 최소한의 직접 구현 | 아래 참고 |

컴포넌트는 처음에 Radix를 쓰려 했으나, 실제로 필요한 것을 세어 보니 라이브러리가 필요 없었다.

| 필요한 것 | 선택 | 이유 |
|---|---|---|
| 탭 | `<Link>` + `aria-current` | 주소가 바뀌는 탭은 ARIA tablist가 아니라 이동이다. 링크로 두면 딥링크·새로고침·JS 없는 환경이 전부 공짜로 해결된다 |
| 대화상자 | 브라우저 `<dialog>` + `showModal()` | 포커스 가두기·Esc 닫기·바깥 영역 비활성화를 브라우저가 해 준다. 직접 만들면 대개 어딘가 빠진다 |
| 선택 | 브라우저 `<select>` | 직접 만든 드롭다운은 키보드·스크린리더·모바일에서 기본만 못하다 |
| 상태 변경 | 값이 다른 제출 버튼 4개 | 드롭다운+저장 2단계를 1단계로 줄였고, JS 없이도 동작한다 |

결과적으로 UI 의존성은 아이콘(lucide-react)과 클래스 병합 유틸 두 개뿐이다.
| 레이아웃 | 업무 도구형 | 대국민 사이트 구조는 부적합 |
| 접근성 | **실질 준수** | 유일한 법적 의무 영역 |

### 8.3 화성특례시 BI 적용 **[확인]**

「화성특례시 상징물(BI) 기본 디자인 가이드라인」 BS 1-03 (2024-10-25 선포)

| 색 | 규정 | HEX |
|---|---|---|
| **HS Blue** (주조색) | PANTONE 7686 C · C100 M75 Y0 K0 · R0 G70 B150 | **`#004696`** |
| HS Orange (보조색) | PANTONE 1505 C · C0 M70 Y100 K0 · R220 G110 B45 | `#dc6e2d` |
| HS Light Gray | PANTONE Cool Gray 3 C · K30 | `#c6c6c6` |

- 화성시는 **HEX를 공식 규정한 적이 없다.** 위 값은 규정 RGB의 환산값이며, 시청 BI 페이지가 실제 로드하는 전용 CSS(`add_2025-04-02.css`)에서 `#004696`/`#dc6e2d`로 렌더링됨을 확인했다
- 배포 PNG 아트워크의 픽셀 실측값 `#0054A6`/`#F36F21`은 CMYK→sRGB 변환 산출물이다
- 발표자료에는 **"HEX는 시 공식 규정에 없어 규정 RGB 환산값을 사용"**이라고 각주를 단다
- 명도대비 `#004696` : 흰색 = **9.06:1 (AAA)**. HS Orange는 3.33:1이라 **본문 텍스트로 쓰지 않고** 강조·아이콘·보더에만 쓴다
- **BI 지정서체가 Pretendard Variable**이다. KRDS의 Pretendard GOV 선택과 정확히 맞물린다
- BI 핵심가치는 **V.I.B.E.**(Vitality/Intelligence/Balance/Expand)이고, 보조색 공식 별칭이 **"화성 Connection Orange"**, 주조색이 **"화성 Intelligent Blue"**다 → 발표에서 *"화성시가 스스로 Connection을 브랜드 가치로 내걸었습니다"*로 연결한다

## 10. 기대효과 및 행정 적용방안

### 10.1 행정 비용 절감 — 추정치 없이

한국행정연구원(2011) 조사값을 그대로 쓴다 **[확인]**.

```
인계인수 만족 시 업무파악    2.64개월
인계인수 불만족 시           3.78개월
                            ────────
차이                         1.14개월      = 3.78 대비 30.2%
```

**1.14개월과 30.2%는 같은 사실의 두 표현이다. 곱하지 않는다.**
화성시 숫자로 바꿀 때 곱하는 것은 **「연간 전보 인원 × 1.14개월」** 하나뿐이다.
**전보 인원은 화성시 공개자료로 확인한 뒤에만 발표에 넣는다.** (13장)

보조 지표: *"대면 인계인수는 길어야 반나절, 통상 30분"* — 30분에 넘길 수 있는 일머리의 양이 곧 문제의 크기다.

### 10.2 확산 가능성

부서·업무 분류 테이블만 교체하면 **경기도 31개 시·군, 전국 243개 지자체**에 그대로 적용 가능한 구조다.

### 10.3 수명과 이관 경로 (정직하게)

행안부 **「온AI」**가 2027년 이후 지자체에 온다(중앙부처엔 2026-04-30 이미 도착했다). 일머리는 그때까지의 공백을 메우고, **축적한 데이터는 표준 구조로 이관 가능**하도록 설계했다.

이관 경로는 두 갈래다.

| | 무엇이 넘어가나 |
|---|---|
| **문서** | 별지 제2호·제12호서식 **HWPX**. 온AI가 오기 전에도 온나라에 그대로 얹힌다 |
| **데이터** | 업무·이력·결재 기록. 표준 서식에 대응되도록 칸을 설계했다 |

> 문서 쪽 이관은 **지금 당장 동작한다.** 플랫폼이 바뀌기를 기다리지 않아도 된다는 뜻이고,
> 이것이 「행정 적용 가능한 제안」이라는 심사축에 대한 가장 구체적인 답이다.

### 10.4 KRDS 자체 검증 결과

「자체 검증 체크리스트」(2024.11) 기준 자체 검증을 수행하고 결과서를 첨부한다.

- 전체 311개 (스타일 21 / 컴포넌트 170 / 기본패턴 47 / 서비스패턴 73)
- 적용 트랙: **자체 상징** (화성특례시 BI 사용) → 적용 대상 301개에서 시작
- 검증 환경: Windows 10+ / Chrome 최신 / 1920×1080 / 확대 100%
- 검증 범위: **화면 10개 이상 표집**(지침 권장) · 판정 `P`/`F`/`E`/`N/A`
- **목표: 적용 대상 준수율 90%**
