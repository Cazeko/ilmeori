### 4. AI 실제 연결 — 1일

`src/lib/handover-draft.ts` 는 **규칙 기반 조립**이다. Claude를 부르지 않는다.
화면 문구와 `ai_model` 값은 정직한 쪽으로 이미 고쳤으므로 **지금 발표해도 무너질 문장은 없다.**

| | 내용 |
|---|---|
| A | 실제로 Anthropic API를 붙인다 |
| ~~B~~ | ~~문구를 정직하게 바꾼다~~ → **완료** |
| **C** | **규칙으로 뼈대를 뽑고 AI가 문장만 다듬는다.** 근거 추적은 규칙이라야 정확하고, AI도 진짜가 된다 |

**붙일 자리가 정해졌다.** 오늘 「1-다. 현안사항」이 대화를 읽게 되면서, 규칙이 고른
근거(누가 언제 한 말인지)와 그 원문이 손에 들어왔다. C안은 여기 한 칸만 모델에 넘기면 된다.

```
규칙  대화 N건 중 기한·질문·결정 대기 표현이 있는 것을 고른다  →  근거 (사람·날짜·원문)
모델                                                        →  그 근거만으로 문장을 만든다
```

지킬 것 셋.
1. **근거를 고르는 일은 규칙이 한다.** 모델이 고르면 왜 골랐는지 화면에 적을 수 없다.
2. **화면을 그리는 경로에 모델을 끼우지 않는다.** 인계자가 「확인」을 누를 때만 부른다.
   심사 도중 API가 느리면 화면이 통째로 멈춘다.
3. **실패하면 지금 문장으로 떨어뜨린다.** 최악이 오늘 상태이므로 잃을 것이 없다.
   그때 `ai_model` 을 실제 모델 이름으로 바꾼다 — 그 칸은 무엇으로 만들었는지 적는 감사 기록이다.

## 이번에 붙인 것 (2026-08-08) — 결재 화면

데이터 모델(0016·0017)은 8/8 아침에 들어갔고, 이건 그 위에 올린 화면이다.
**결재는 이 제품을 열어 볼 이유** 그 자체이므로, 없는 동안에는 나머지 화면이
아무리 좋아도 「그래서 결재는요?」에서 끝났다.

### 무엇이 생겼나

| 화면 | 하는 일 |
|---|---|
| `/approvals` | 결재함. 대기·예정·처리·기안 중·완료·전체 여섯 칸. **대기에만 숫자 배지** |
| `/approvals/new` | 기안. 업무를 고르고 서식·제목·본문·보존연한·협조자를 정한다. 결재선은 미리 채워 보여 준다 |
| `/approvals/[id]` | 결재란 · 본문 · 의견 · 그리고 「지금 내가 할 일」. 차례가 오면 서명·반려 상자가 그 자리에 나타난다 |
| `/works/[id]?tab=approval` | 탭이 넷에서 **다섯**이 됐다. 결재 문서의 집은 결재함이 아니라 업무다 |
| `/` | 「내 차례인 결재가 N건 있습니다」 — 인계 다음, 업무 요약보다 위 |

### 지금 내 차례인가 — 같은 판정을 두 곳에서

DB에는 이미 `app.step_block_reason()` 이 있다. 그런데 **화면이 그것을 부를 수 없다** —
`app` 스키마는 PostgREST 에 노출되지 않기 때문이다(0017 §1). 결재함은 문서를 여럿
늘어놓는 화면이라, 겉면 함수를 public 에 하나 더 만들어도 문서 수만큼 왕복이 늘어난다.

그래서 `src/lib/approval.ts` 에 **같은 규칙을 같은 문구로** 적었다. `sectionLockActive()`
와 같은 자리이고 같은 이유로 남겨 둔 중복이다. 지켜야 하는 것은 하나 —
**규칙이 바뀌면 두 파일을 함께 고친다.** 어긋나도 서명이 잘못 찍히지는 않는다.
서명은 절차로만 찍히고 절차가 다시 판정하므로, 최악은 「눌러도 안 되는 버튼」이다.

### 붙이면서 물린 것

| 무엇 | 어떻게 됐나 |
|---|---|
| **조직도에 위가 없었다** | 결재선 자동 생성은 「기안자보다 rank 가 작은 같은 부서 사람」을 훑는데, 목업의 자원순환과에는 주무관 둘뿐이라 결과가 언제나 빈 결재선이었다. 정다은(팀장)·한상우(과장)·문지호(단장)·박도윤(의회법무과)을 더했다. **rank 는 문자열이 아니라 숫자로 판정하므로** 「단장」도 과장급(30)으로 들어간다 |
| **`session.ts` 가 rank 를 안 읽고 있었다** | 0016 이 칸을 더했는데 `getViewer()` 의 select 목록에는 없었다. 타입은 `data as Profile` 로 통과하고 실제 값은 undefined 라, 결재선 자동 생성이 **아무 오류 없이 빈 결재선**을 준다(비교가 전부 false 가 된다). 화면을 만들지 않았으면 안 잡혔을 버그다 |
| **결재선 복사가 기안란까지 지우고 있었다** | 지우고 다시 넣는 방식이라, 그 사이 insert 가 실패하면 **기안란이 없는 문서**가 남는다. 그 문서는 상신도 안 되고(「결재선에 기안란이 없습니다」) 화면 어디에도 이유가 안 나온다. 기안란은 두고 나머지만 갈아 끼우도록 고쳤다 |
| **서명하고 홈에 가면 숫자가 그대로였다** | 액션이 `/approvals` 와 그 문서만 다시 그리게 하고 있었다. 홈의 「내 차례인 결재 N건」은 옛 숫자를 들고 있었고, 한 번 틀린 숫자는 그때부터 아무도 안 믿는다 |
| **결재함이 조용히 100건에서 잘렸다** | 상한 자체는 필요하다(부서 문서가 전부 보이는 화면이다). 잘랐다는 사실을 화면이 말하도록 고쳤다 — 말하지 않는 상한은 「전부 다 봤다」로 읽힌다 |
| **결재란 칸 수에 상한이 없었다** | 결재란은 표가 아니라 **서식**이라 칸이 옆으로 늘어난다. 12칸으로 막았다. ⚠ **앱에만 있는 상한이다** — DB 쪽 제약은 다음 마이그레이션의 일이고, 그때까지 `actions/approvals.ts` 의 주석이 그 사실을 적어 둔다 |
| **데모 모드에서 「대기 1건」인데 열면 아무것도 없었다** | 서명 상자는 `canMutate` 일 때만 그리는데, 그 경우 아무 말도 하지 않고 있었다. 「지금 내 차례입니다 · 데모 모드에서는 서명할 수 없습니다」로 사실을 적는다 |
| **결재란 사선을 그림으로만 그렸다** | 전결 뒤 칸은 아무도 서명하지 않는다. 비워 두면 「아직 안 한 사람」으로 읽히므로 사선을 긋는데, 그림만으로는 스크린리더에 아무것도 안 남는다. 「전결로 끝나 결재하지 않았습니다」를 글자로 함께 둔다 |
| **반려 사유 칸과 서명 의견 칸을 한 폼에 담을 뻔했다** | 버튼 두 개가 한 입력칸을 나눠 쓰면 「의견은 선택, 사유는 필수」라는 서로 다른 규칙을 한 칸에 걸어야 한다. 폼을 둘로 갈랐고, 반려는 `<details>` 를 펼쳐야 나온다 — 펼치는 손짓 한 번이 확인 절차를 대신한다(인계 취소와 같은 판단) |

### 화면이 사실을 말하는가

- **업무를 못 봐도 문서 한 장은 본다.** 협조자에게는 업무 제목 자리에 「열람 권한이 없는 업무」라고 적는다. 비워 두면 화면이 고장 난 것으로 보이고, 제목을 적으면 RLS 가 막은 것을 화면이 흘리는 셈이 된다
- **없는 문서와 못 보는 문서를 구분하지 않는다.** 업무에서 하는 것과 같은 답을 한다
- **직위는 서명 당시의 것**이라고 결재란 아래에 적어 두었다. 인사이동 뒤에 옛 문서의 결재란이 바뀌면 그건 문서 위조다
- **도장 그림을 넣지 않았다.** 시제품의 인장 이미지는 위조 인상을 주고 실제로는 아무것도 보증하지 않는다

### 이어서 붙인 것 — 화면 정비 (색 두 층 · 본문 폭)

계획서 §7의 8/15 몫인데, 결재 화면이 새로 열두 개 붙는 김에 먼저 쳤다. 화면 수가
더 늘어난 뒤에 손대면 그만큼 비싸진다.

| 무엇 | 어떻게 됐나 |
|---|---|
| **`--color-white` 를 덮어쓸 뻔했다** | 계획서에는 그렇게 적혀 있었는데, Tailwind 는 `bg-white` 와 `text-white` 가 **같은 토큰**이다. 덮어쓰면 판만 내려가는 것이 아니라 색 위에 얹은 글자까지 내려간다 — 재 보니 `bg-danger` 위 흰 글자가 4.56 → **4.37 로 미달**이었다. 판 전용 토큰 `--color-surface: #fafafa` 를 새로 두고 `bg-white` 55곳을 `bg-surface` 로 바꿨다. 인쇄용 `print:bg-white` 하나만 순백으로 남겼다 |

## 이번에 붙인 것 (2026-08-07 밤) — 인계서 보충

### 화면이 시키는 일을 화면이 못 하게 막고 있었다

인계 화면은 이렇게 적고 있었다.

> "그대로 제출하는 문서가 아니라 인계자가 확인하고 고쳐야 하는 초안입니다."

그런데 고칠 수단이 없었다. 인계에 딸린 동작은 다섯 개(시작·확인·실행·취소·시연 되돌리기)뿐이고
그중 초안에 손대는 것이 하나도 없었다. 특히 3번 항목은 코드가 **스스로 표시(`needsHuman`)까지
달아 두고** 적을 칸을 주지 않았다.

```
3. 주요 물품 및 예산 등 인계·인수가 필요한 사항
   "이 시스템에는 물품·예산 정보가 없습니다. 재무회계시스템과
    물품관리대장을 확인해 인계자가 직접 적어야 합니다."     needsHuman: true
```

심사에서 「그럼 여기는 어떻게 적나요」라고 물으면 답이 「인쇄해서 손으로요」였다.
미구현이 아니라 **화면이 어긋나는 지점**이다.

### 전문 편집이 아니라 항목별 덧붙임

이 제품의 주장은 「문장마다 어느 기록에서 나왔는지 적는다」이다. 사람이 규칙으로 뽑은
문단을 덮어쓰면 그 문장은 근거를 잃고, **옆에 붙은 근거 꼬리표가 그 순간 거짓말이 된다.**
근거를 붙이려고 만든 장치가 근거를 무너뜨리는 셈이다.

그래서 규칙이 뽑은 본문은 손대지 못하게 두고, 사람이 적은 것을 항목마다 따로 쌓는다.

```
1-다. 현안사항 및 문제점
  · 2026년 음식물류폐기물 …                    ← 규칙이 뽑음, 근거 꼬리표 유지
    [대화 — 배도현 주무관, 7월 30일 · 기한 · 질문]
    "2027년도 예산 요구서에…"
  근거: 업무 문서의 「현안 및 유의사항」 항목 · 대화 10건 중 …

  ─────────────────────────────
  인계자 보충 · 박준호 주무관, 8월 7일          ← 사람이 쓴 것, 색도 자리도 다르다
    대행료 단가 협의는 예산재정과와 8/12 회의 예정입니다.
```

셋이 한꺼번에 풀린다 — 3번 항목은 원래 비어 있으니 그 칸이 곧 본문이 되고, 근거 추적이
안 깨지고, **「기계가 뽑고 사람이 보탠다」가 문구가 아니라 화면으로 보인다.**

> 색을 accent(보라)로 쓰지 않았다. 이 화면에서 accent 는 「기계가 뽑은 것·근거 꼬리표」의
> 색이다. 사람이 적은 줄에 그 색을 쓰면 구별하려고 만든 두 가지를 같은 색으로 칠하게 된다.

### 고쳐 쓰는 버튼은 두지 않았다

보충에는 적은 사람과 시각이 붙고 그 날짜가 **인쇄본에 그대로 찍힌다.** 몸통만 나중에
바뀔 수 있으면 종이에 찍힌 날짜가 거짓이 된다. 지우고 다시 적으면 새 시각이 붙으므로
그쪽이 사실에 가깝다. DB도 같다 — `UPDATE` 는 정책도 권한도 없다(GRANT 층에서 42501).

지우기는 **실행 전에만** 연다. 0008의 인계 취소와 같은 판단이다. 실행이 끝나면
0011의 완료된 인계 잠금과 같은 규칙을 따라 더하지도 지우지도 못한다(정책이 막는다).

### 칸 이름은 시행규칙이 정한다

`block_key` 값 일곱 개를 DB의 check 제약으로 묶었다. 이 칸들은 우리가 정한 것이 아니라
「행정업무의 운영 및 혁신에 관한 규정 시행규칙」 별지 제12호서식이 정한 것이고,
앱이 여덟 번째 칸을 만들 수 있으면 그건 이미 그 서식이 아니다.
폼을 거치지 않은 요청이 엉뚱한 칸 이름을 실어 보내도 여기서 걸린다 — 없었다면
**화면 어디에도 안 보이는 행**이 조용히 쌓였을 것이다.

항목 이름(heading)이 아니라 키를 저장한다. 문구를 한 번 다듬는 순간 예전에 적어 둔
보충이 어느 칸 것인지 알 수 없게 되기 때문이다.

### 붙이면서 물린 것

| 무엇 | 어떻게 됐나 |
|---|---|
| **조각(#)을 그냥 이어 붙이면 주소가 깨진다** | 항목이 일곱 개라 적고 나서 맨 위로 튕기면 무엇이 달라졌는지 못 본다. 그런데 `withFeedback` 이 `?msg=` 를 뒤에 붙이므로 `/handover#block-3-assets?msg=…` 가 되어 **조각 이름이 `block-3-assets?msg=…` 로 읽힌다.** 조각을 맨 뒤로 옮겼고, 이 함수는 앱의 모든 결과 알림을 실어 나르므로 회귀 시험(`tests/feedback-url.test.mjs`)을 붙여 `npm run check` 에 넣었다 |
| **성공은 항목으로, 실패는 맨 위로** | 실패까지 항목으로 튕기면 무엇이 잘못됐는지 적힌 알림 판을 지나치게 된다 |
| **배포와 마이그레이션은 같이 움직이지 않는다** | 코드는 깃헙에 올리면 Vercel 이 배포하고 0014는 사람이 SQL Editor 에서 돌린다. 그 사이에 인계 화면을 열면 표가 없어 질의가 실패하고, **보충 한 칸 때문에 제품의 결론인 화면이 통째로 오류 화면**이 된다. 「표 없음」(42P01·PGRST205)만 0건으로 이어 받고 서버 로그에 무엇을 돌려야 하는지 적는다. 나머지 오류는 지금까지처럼 던진다 |
| **목업 모드에는 보충 칸을 아예 안 그린다** | 데모의 변경분은 쿠키(4KB)에 담기는데 보충은 한 줄이 1000자까지라 한 번만 적어도 넘치고, 넘친 쿠키는 브라우저가 조용히 통째로 버린다. `canMutate` 와 같은 판단이다 |
| **eslint 가 목업 쪽 미사용 인자를 잡았다** | `no-unused-vars` 의 `after-used` 규칙 때문에 **인자가 하나뿐인 함수만** 걸린다(`_viewer, id` 는 안 걸린다). 목업 구현을 두지 않고 `logAccess` 와 같은 자리에서 갈랐다 |
| **PGlite 가 초록불인데 SQL Editor 가 42501 을 냈다** | 0015가 `alter function ... set app.executing_handover = '1'` 로 함수에 사용자 정의 매개변수를 붙이려 했다. 그건 **superuser 전용**이고 Supabase 의 postgres 는 superuser 가 아니다. PGlite 는 superuser 로 돌아서 그대로 통과했다 — **이 검사는 원리상 이 부류를 못 잡는다.** 호출 스택을 직접 보는 쪽(`GET DIAGNOSTICS ... PG_CONTEXT`)으로 바꿨다. 아무 권한도 필요 없고, execute_handover 본문을 복사하지 않아도 된다. 같은 실수가 다시 나지 않도록 `db:verify` 에 **글자로 잡는 검사**를 넣고, 일부러 되돌려 빨간불이 켜지는 것을 확인했다 |
| **`[[:space:]]` 는 로케일이 정한다** | 빈 글 판정을 그 낱말 부류로 적으면 어떤 글자가 공백인지가 DB 설정에 달린다. 전각 공백(U+3000)이 로컬에서는 잡히고 실물에서는 안 잡힐 수 있다. 가릴 글자를 코드포인트로 직접 적어 로케일에서 떼어 냈다. `create table if not exists` 로는 이미 적용된 제약이 안 바뀌므로 0015에서 갈아 끼운다 |

### 검증

```
npm run check          타입 · safeNext · withFeedback 8건 · 마이그레이션 · RLS 125개 · 시드 · 되돌리기
npm run test:browser   105건 (인계서 보충 26건 추가 — 그중 21건은 0014·0015를 돌린 뒤라야 돈다)
```

RLS 27개가 늘었다. 인계자만 적을 수 있는가, 인수자는 읽되 못 적는가, 제3자는 못 읽는가,
서식에 없는 칸은 막히는가, 빈 글·줄바꿈만 있는 글·1000자를 넘는 글은 막히는가,
**적어 둔 것을 고칠 수 있는가(권한층에서 42501)**, 실행 전에는 지울 수 있는가,
실행 뒤에는 더하지도 지우지도 못하되 **읽히기는 하는가**,
그리고 **인수자가 인계 건을 가로챌 수 있는가**(0015).

브라우저 왕복은 전부 **자바스크립트를 끈 상태로** 돈다 — 적고, 저장되고, 그 항목으로
돌아오고, 종이에 「인계자 보충 —」으로 실리고, 손으로 적을 빈칸이 사라지고,
**인수자에게는 보이되 적을 칸이 없고**, 지우면 다시 「사람이 직접 적어야 합니다」로
돌아가는 것까지.

### 코드리뷰에서 나온 것 (다섯 관점 → 재현 → 살아남은 것만)

관점을 넷으로 나눠 각자 백지에서 돌리고 — 보안·RLS / 마이그레이션·SQL / 화면과 종이가
사실을 말하는가 / 시험이 실제로 무엇을 증명하는가 — 고친 뒤에 **다섯 번째로 「앞의 넷이
놓친 것」만 찾는 판**을 한 번 더 돌렸다. **지적 38건 → 고친 것 21건.**

다섯 번째 판이 제값을 했다. 앞의 넷을 고치고 나서야 드러나는 것이 둘 있었다
(완료 도장 위조, 그리고 유니코드 공백). **고친 뒤에 한 번 더 보지 않았으면 둘 다 나갔다.**

가장 큰 하나는 **이번 변경이 만든 것이 아니라 이번 변경이 쓸모 있게 만든 것**이었다.

| 무엇이 잘못돼 있었나 | 어디서 잡았나 |
|---|---|
| **인수자가 남의 인계서를 통째로 가로챌 수 있었다.** 0014의 보충 정책은 `handover.from_profile_id` 를 「이 문서의 저자」로 믿는데, 0002의 `handover_update` 가 당사자 **둘 모두**에게 UPDATE 를 열어 두고 어떤 칸을 고치는지는 보지 않았다. 인수자가 그 칸을 자기로 바꾸면 ① 자기 문장을 인계서에 넣고 ② 원래 인계자는 자기 문서에 못 적게 되고 ③ `status='completed'` 로 못질까지 할 수 있다(0011이 되돌리기를 막으므로 영구히). 업무가 넘어가지는 않지만 **서명란에 인계자 이름이 찍힌 문서의 저자가 바뀐다** → 0015 | 코드리뷰 → PGlite 재현 → 고친 뒤 재재현 |

## 이번에 붙인 것 (2026-08-07 밤) — 실시간 공유 체계

과제 요구 일곱 개 중 마지막으로 비어 있던 칸이다.

### 신호는 화면을 그리지 않는다

웹소켓으로 오는 것은 「이 업무에서 무언가 바뀌었다」는 한 줄뿐이다.

```json
{ "kind": "section", "work_id": "…", "actor": "…", "at": "…" }
```

제목도 본문도 파일 이름도 대화 한 줄도 실려 오지 않는다. 그 한 줄을 받으면 브라우저는
**서버에 다시 묻고**(`router.refresh()`), 화면에 나타나는 것은 언제나 RLS 를 통과한
데이터다. 지연 판정이나 잠금 만료 같은 파생 상태도 서버 시계로 계산된 값 그대로다.

이렇게 한 이유가 있다. **broadcast 의 권한 판정은 채널에 들어올 때 한 번뿐이고 행 단위
필터가 없다.** 페이로드에 실은 것은 그 채널의 모두에게 그대로 간다. Supabase 가 주는
`realtime.broadcast_changes()` 는 바뀐 행 **전체**를 싣는다 — 그래서 쓰지 않고
`realtime.send()` 로 신호만 조립해 보낸다.

### 토픽 이름이 곧 권한 경계다

채널 이름은 `work:<업무 id>` 이고, `realtime.messages` 의 정책이
**`app.can_read_work()`** 를 부른다. 업무 화면을 여는 판정과 **같은 함수**다.

```sql
create policy work_topic_read on realtime.messages
  for select to authenticated
  using (
    realtime.messages.extension in ('broadcast', 'presence')
    and app.can_read_work(app.topic_work_id((select realtime.topic())))
  );
```

업무를 볼 수 없는 사람은 웹소켓으로도 그 업무의 신호를 받지 못하고, 접속자 목록에도
들어오지 못한다. 실제로 찔러 보면 채널 참가 자체가 `Unauthorized` 로 거부된다.

> 토픽 문자열을 정책 안에서 맨몸으로 uuid 캐스팅하면 안 된다. 토픽이 `lobby` 같은 값일 때
> 캐스트 예외가 나고 **판정 질의 전체가 실패한다.** and 의 평가 순서는 보장되지 않으므로
> `like 'work:%'` 가드도 안전하지 않다. `app.topic_work_id()` 로 봉인했고, 이상한 토픽
> 다섯 가지를 시험에 박아 뒀다.

### 신호를 보내는 것도 DB다

서버 액션 27개에 한 줄씩 넣는 대신 표에 트리거를 달았다. 이력을 트리거가 남기는 것과
같은 이유다 — 개발자가 빠뜨릴 수 없고, 앱을 거치지 않은 변경도 새어 나가지 않는다.

**이력에 남지 않는 변경까지 신호가 나가는 것**이 이 방식의 값이다. 문서 항목 잠금은
일부러 이력에 남기지 않는데(남기면 이력이 잠금 기록으로 뒤덮인다), 「○○○ 편집 중」이
상대 화면에 곧바로 떠야 하는 것은 바로 그 변경이다.

### 스크립트가 없으면 아예 나타나지 않는다

이 제품의 화면은 자바스크립트 없이 전부 도는 것이 전제이고, 실시간은 원리상 그럴 수 없다.
그래서 인쇄 버튼과 같은 판단을 했다 — **스크립트가 살아 있을 때만 그린다.**
없으면 상자가 아예 없고, 새로고침하면 최신 상태가 나온다.

편집칸을 열어 둔 사람의 화면은 가로채지 않는다. 쓰던 글이 위태로워지기 때문이다.
그때는 「다른 사람이 대화를 고쳤습니다 · 쓰고 있는 내용을 지키기 위해 화면을 그대로
두었습니다」라고 알리고, 반영할지는 그 사람이 정한다.

### 접속자 표시 — 이것만은 DB가 보증하지 못한다

누가 접속했다는 사실은 각자의 브라우저가 알리는 것이라 원리상 위조할 수 있다.
그래서 **이름은 서버가 준 참여자 목록에서만 찾고**, 목록에 없는 사람은 「다른 직원 N명」으로
수만 센다. 브라우저가 보내는 것은 접속했다는 사실뿐이고, 채널에 들어온 것 자체는
RLS 가 판정한 결과다.

발표에서 물으면 이렇게 답한다. **「이 한 줄만은 DB가 보증하지 못합니다. 그래서 이름을
그 줄에서 가져오지 않았습니다.」**

### 실물에 올린 뒤에 나온 것 (0012·0013 적용 후)

PGlite 검사 98개와 브라우저 79건이 전부 초록불인 상태에서 **실물에 붙이자마자 둘이 더 나왔다.**
둘 다 제품이 아니라 **검사가 틀린 경우**였는데, 둘 다 코드만 읽어서는 절대 안 나온다.

| 무엇 | 실제 |
|---|---|
| **배달되는 페이로드에는 칸이 하나 더 있다.** 우리가 넣은 넷 말고 `id` 가 붙는다 | Realtime 서버가 붙이는 **메시지 자체의 uuid** 다(`meta.id` 와 같은 값). 우리 데이터가 아니라 유출은 아니지만, PGlite 스텁은 **저장된 행**만 재현하고 배달 시점은 재현하지 못한다. 그래서 로컬 검사는 넷을 보고 실물 확인은 다섯을 본다 — 양쪽 주석에 그 차이를 적어 뒀다 |
| **시험이 멀쩡한 기능을 결함으로 보고했다.** 「편집 중에 쓰던 글자가 지워진다」 | `waitForLoadState("networkidle")` 는 **서버 액션의 리다이렉트를 기다려 주지 않는다.** 잠잠해진 시점에는 아직 옛 화면이라, 편집칸이 아니라 「항목 추가」칸에 글자를 넣고 0.6초 뒤 화면이 갈렸다. 주소에 `edit=` 가 붙을 때까지 기다리고, 채울 칸을 폼으로 특정하도록 고쳤다 |

두 번째가 특히 위험한 종류다. **시험이 거짓 빨간불을 내면 멀쩡한 코드를 고치게 된다.**
값이 서버 기본값(`"내용"`)으로 되돌아간 것과 페이지가 다시 로드되지는 않은 것을 함께 보고 나서야
「갱신은 일어났지만 이동이 늦었다」가 잡혔다.

### 알고도 고치지 않은 것

| 무엇 | 왜 |
|---|---|

| 로그인한 본인의 이메일은 여전히 페이지 원본에 있다(`AppShell` 이 Profile 을 통째로 받는다) | 이번 변경과 무관한 기존 코드이고, 남의 것이 아니라 자기 것이다. 셸을 건드리는 것은 마감 앞에서 위험 대비 이득이 낮다 |

`test:realtime` 은 확인용 업무를 하나 만들었다가 끝나면 지운다(제목이 「[실시간 검증]」으로
시작한다). 시연 데이터를 건드리지 않기 위해서다. 도중에 죽어 남은 것이 있으면 다음 실행이
먼저 치운다.

## 이번에 붙인 것 (2026-08-07 오후)

### 1. 인계서가 대화를 읽는다

`handover-draft.ts` 는 문서·이력·첨부만 읽고 **대화(comment)는 한 줄도 읽지 않았다.**
그래서 「1-다. 현안사항 및 문제점」은 문서 항목 제목에 "현안"이나 "유의"가 들어 있을 때만
채워졌고, 없으면 "확인된 현안사항이 없습니다"로 끝났다.

그런데 인계 대상 업무에는 이런 대화가 붙어 있다.

> "2027년도 예산 요구서에 대행료를 반영해야 하는데, 최종보고가 8월 14일이면 요구서 제출 기한과 겹칩니다."

**이게 정확히 현안사항이다.** 제품이 "왜 그렇게 정했는가는 대화에 있다"고 화면에서 말해 놓고
인계서는 그 대화를 통째로 건너뛰고 있었다 — 논지의 심장이 비어 있었던 셈이다.

방식은 **뜻을 판정하지 않고 표현을 찾는 것**이다. 기한·질문·결정 대기·이견·약속 다섯 갈래의
표현을 찾고, 고른 이유를 이름표로 함께 적고, **요약하지 않고 원문 그대로 인용**한다.
규칙이 왜 이 대화를 골랐는지 화면에 그대로 적을 수 있어야 하기 때문이다.

```
· 2026년 음식물류폐기물 수집·운반 대행 원가산정 용역
  [문서 — 4. 현안 및 유의사항]
  ...
  [대화 — 배도현 주무관, 2026년 7월 30일 · 기한 · 질문]
  "2027년도 예산 요구서에 대행료를 반영해야 하는데, ..."
```

근거 꼬리표에는 **몇 건 중 몇 건인지** 적는다("대화 10건 중 … 2건"). "대화에서 뽑았습니다"만
적으면 나머지를 읽지 않아도 된다는 뜻으로 읽힌다.

곁들여 고친 것: 업무 한 건마다 `getWorkDocument()` 를 세 번씩 부르고 있었다. 한 번으로 모았다.

### 2. 인계서 인쇄 서식

`@media print` + 인쇄 전용 문서(`print-sheet.tsx`). 브라우저 인쇄로 별지 제12호서식 모양 A4가 나온다.
구분·소속·직급·성명 표, 항목 일곱 개, 인계자·인수자·입회자 서명란, 맨 아래 출처 한 줄.

화면용 카드에 인쇄 규칙을 덧씌우지 않고 **두 벌을 따로 그린다.** 화면은 확인하는 도구이고
종이는 결재에 올리는 문서라 필요한 것이 다르다 — 화면에는 항목마다 근거 꼬리표가 붙어야 하고,
종이에는 그것이 서식을 어지럽힌다. 한쪽에 맞추면 반드시 다른 쪽이 어색해진다.

인쇄 버튼은 `window.print()` 말고는 방법이 없어 이 제품에서 **유일하게 스크립트가 필요한 곳**이다.
그래서 스크립트가 살아 있을 때만 그린다(`useSyncExternalStore`). 없으면 버튼이 아예 나타나지
않고 「Ctrl+P」 안내만 남는다 — 눌러도 아무 일도 안 하는 버튼보다 낫다.

### 3. 「이 업무가 보이는 이유」와 같은 주소·다른 계정

접근제어는 잘 돌수록 화면에 아무것도 보이지 않는다. 잘 막혀 있다는 것은 아무 일도 일어나지
않는다는 뜻이라서 그렇다. 「RLS 시험 몇 개」는 발표자료의 문장이고, 문장은 열세 팀이 다 쓴다.

업무 상세에 접히는 한 줄을 뒀다. 판정 순서는 `app.can_read_work()` 와 **같다.**

> **이 업무가 보이는 이유** — 참여자(열람)로 추가되어 있습니다
> 공개 범위가 「부서 공개」라, 자원순환과 직원과 참여자 3명에게만 열립니다.
> [이 주소를 다른 계정으로 열어 보기]

버튼을 누르면 세션이 끊기고, 계정을 고르면 **같은 주소로 돌아온다.** 볼 수 없는 계정으로 오면
「없습니다」가 뜬다. 새 질의는 0건이다 — 화면에 이미 온 데이터로만 문장을 만든다.

### 곁들여 잡은 것

| 무엇이 잘못돼 있었나 | 어디서 잡았나 |
|---|---|
| **`notFound()` 는 스크립트를 끈 브라우저에서 빈 화면이 된다.** 응답은 404인데 `<body>`가 비어 있고 본문은 `__next_f` 스크립트 안에만 있었다. 상위 레이아웃이 먼저 흘러 나간 뒤라 Next가 HTML로 못 그린다 | 브라우저 시험 |
| **`safeNext` 가 오픈 리다이렉트를 막지 못했다.** `/%09/evil.example.com` 이 검사를 통과했다 — 브라우저 URL 파서는 해석 전에 탭·개행을 **지우고** 읽는데, 검사는 지우기 전 문자열을 보고 있었다. Location 헤더에 원문이 실려 나가 프로토콜 상대 URL이 됐다 | 코드리뷰 → 실측 |
| 실제 프로젝트의 `handover.ai_model` 이 아직 `claude-opus-5` 였다. 시드를 고쳤지만 `on conflict do nothing` 이라 이미 들어간 행은 그대로였다 | 인쇄 서식 실측 |
| 인쇄 버튼이 화면에 **둘** 있었다 | 브라우저 시험 |
| 「없거나 보이지 않습니다」가 **목업 모드에서도** RLS를 근거로 댔다. 그 모드에는 Supabase가 아예 없다 | 코드리뷰 |
| 인쇄본 맨 아래 「생성 08:40」이 실제 조립 시각과 달랐다. 본문은 인쇄할 때마다 다시 조립되므로, 그 사이 붙은 대화가 실리면서 시각만 옛것이 찍혔다 | 코드리뷰 |
| 근거 꼬리표의 「언급된 N건」이 업무별 상한(3건)에 걸려 빠진 것을 세지 않았다. 잘라 놓고 말하지 않으면 「다 실었다」로 읽힌다 | 코드리뷰 |
| 인계 대상이 0건이면 「1-가·1-나」가 제목만 남고 본문이 통째로 비었다 (다른 과 인수자 + 부서 공개 업무) | 코드리뷰 |
| 「고칠 수 없는 업무입니다」의 「이 주소 다시 열기」가 편집 주소가 아니라 상세 주소로 갔다 | 코드리뷰 |
| `0001_schema.sql` 이 아직 「AI가 생성한 초안 · 생성 모델 기록」이라고 적고 있었다 | 코드리뷰 |

`notFound()` 건은 **응답 코드와 사람이 읽을 화면을 맞바꾼 것**이다. 페이지가 직접 그리면
스크립트 없이도 보이지만 응답은 200이 된다. 이 주소는 사람이 눈으로 여는 화면이지 기계가
부르는 API가 아니라서 이쪽을 골랐다. 없는 업무와 못 보는 업무를 구분하지 않는 것은 그대로다.

`safeNext` 건은 **검사하는 문자열과 이동하는 문자열이 서로 달랐던 것**이 원인이다.
같은 실수가 다시 나지 않도록 `tests/safe-next.test.mjs` 를 붙이고 `npm run check` 에 넣었다.
제출물에 깃헙 주소와 배포 주소가 함께 들어가므로, 심사위원을 외부 사이트로 보내는 링크 하나면
그걸로 끝이다.

### 검증

```
npm run check          타입 · safeNext 회귀 · 마이그레이션 · RLS 98개 · 시드 · 되돌리기
npm run test:browser   브라우저 왕복 79건 (76건은 자바스크립트를 끈 상태로)
npm run db:realtime    12건 — 실제 프로젝트에 붙어 채널 권한·신호 확인
npm run test:realtime  11건 — 창 두 개로 실시간 왕복
```

`test:browser` 는 playwright 가 필요해서 저장소 의존성에는 넣지 않았다
(없으면 설치 방법을 안내하고 그냥 끝난다). 돌리는 법은 파일 맨 위에 적어 두었다.
**반드시 새로 빌드한 것을 띄우고 돌린다** — `next start` 는 뜰 때의 빌드를 붙들고 있어서,
고치고도 옛 화면을 보며 한참을 헤매게 된다.

코드리뷰는 다섯 관점(초안 정합성 · 보안 · 인쇄 · 문구 정직성 · 회귀)으로 나눠 돌리고,
나온 것을 다시 반박해 살아남은 것만 고쳤다. **36건 보고 → 16건 확정 → 전부 수정.**
반박되어 죽은 20건에는 「인계일에 인쇄한 날짜가 찍힌다」처럼 이미 고쳐진 것,
「220자 절단이 결론을 자른다」처럼 입력 상한(240자)이 이미 막고 있는 것이 섞여 있었다.
