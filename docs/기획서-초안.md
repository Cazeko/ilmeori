## 2. 문제 정의

### 2.1 4단 구조

**1단 — 분산**
같은 업무를 여러 부서·담당자가 함께 처리하지만, 자료는 각자의 PC와 개인 폴더에 있다. 협조하려면 파일을 메신저·전화·공문으로 주고받아야 하고, **어느 것이 최신본인지 아무도 확신하지 못한다.**
→ *과제 원문: "업무자료가 개인 단위로 관리되어"*

**2단 — 비가시성**
이 업무가 지금 어디까지 진행됐는지 팀이 모른다. 담당자에게 직접 물어봐야만 알 수 있고, 담당자가 부재하면 확인할 방법이 없다.
→ *과제 원문: "공동작업에 한계", "실시간 공유 체계가 필요"*

**3단 — 대체 불가**
그런데 노션·구글 독스·슬랙 같은 민간 협업도구를 **쓸 수가 없다.** 업무망과 인터넷망이 분리되어 있고, 공공 업무자료를 외부 SaaS에 반출하는 것도 제한된다.
→ **문제의 본질은 "민간에 이미 있는 것을 또 만드는 것"이 아니라, "민간 도구를 쓸 수 없는 조직에 아직 아무것도 없다"는 것이다.**
※ 확인 필요 항목 — 13장 참조

**4단 — 그리고 이 취약함이 터지는 순간: 인사이동**
평소에도 업무가 개인에게 묶여 있으므로, 담당자가 바뀌면 맥락이 통째로 사라진다. 남는 것은 정리되지 않은 파일 더미와, 떠나기 직전 기억으로 급조한 인계서 한 장이다.
→ *과제 원문: "인수인계에 한계"*

### 2.2 왜 이것이 공익 문제인가

담당자가 바뀌면 민원 처리가 지연되고, 작년의 시행착오를 올해 다시 반복한다.
**이것은 공무원의 편의 문제가 아니라 행정 연속성의 문제이며, 곧 시민이 받는 서비스의 품질 문제다.**

## 3. 해결 방안

### 3.1 한 줄 정의

> 화성시 공무원이 **팀 단위로 업무를 쌓고**, 인사이동이 와도 그 기록을 **끊김 없이 넘기는** 내부 협업 플랫폼.

### 3.2 설계 원리

> **평소 협업의 부산물이 곧 인수인계서가 된다.**

인수인계를 위해 따로 무언가를 작성하게 하지 않는다. 평소 협업 기록(진행상태·메모·변경이력·문서)이 그대로 인계 자료가 되도록 구조를 설계한다.

### 3.3 비중

| 영역 | 비중 | 역할 |
|---|---|---|
| **부서 간 협업** | 70% | 제품의 본체. 일상 사용은 전부 여기서 일어난다 |
| **인수인계** | 30% | 협업이 축적되었을 때 발휘되는 결과. 차별화 지점 |

> 인수인계는 주인공이 아니라 **증거**다. *"협업 도구를 만들었더니 인수인계 문제까지 풀렸다"*가 *"인수인계 도구입니다"*보다 강하다.

## 4. 핵심 기능

### 4.1 과제 요구사항 매핑

| 과제 요구 | 이음의 구현 |
|---|---|
| 문서·업무 **공동편집** | 업무 카드에 소속된 문서를 **섹션 단위로 분할 편집**. 편집 중인 섹션은 잠기고 `○○○ 편집 중` 표시 |
| **진행상태 관리** | 업무 카드 상태(대기/진행중/검토/완료/지연) + 칸반 보드 |
| **변경이력 기록** | 모든 사건을 `activity` 로그로 자동 기록. 업무 카드의 **이력 탭**에서 타임라인으로 열람 |
| **접근권한 관리** | 업무별 참여자 역할(소유/편집/열람)을 **DB의 RLS로 강제** |
| **실시간 공유 체계** | 변경 즉시 반영 + 현재 접속자 아바타 표시 (Supabase Realtime) |
| **팀 단위 협업** | 업무 보드, 댓글, 첨부파일 |
| **업무 인수인계** | 담당 업무 일괄 이관 + **AI 인수인계서 자동 생성** |

### 4.2 화면 (6개)

| 화면 | 역할 |
|---|---|
| `/login` | 로그인 + **데모 계정 원클릭 진입** |
| `/` | 대시보드 — 내 업무 / 팀 현황 / 이번주 마감 / **"작년 이맘때"** 위젯 |
| `/works` | **업무 보드** — 칸반 ↔ 리스트 토글, 부서·담당자 필터 |
| `/works/[id]` | **업무 상세** — 탭 4개: `문서` `대화` `이력` `참여자·권한` |
| `/handover` | 인수인계 — 대상 업무 선택 → 후임 지정 → AI 인계서 생성 → 이관 |
| `/audit` | 감사로그 — 열람·수정 기록 |

> **데모 계정 원클릭이 중요하다.** 심사위원이 웹앱 주소로 접속했을 때 회원가입 화면이 뜨면 대부분 거기서 이탈한다. 로그인 화면에 `[김○○ 주무관으로 보기]` `[박○○ 팀장으로 보기]` 버튼을 배치해 **권한 차이까지 직접 체험**하게 한다.

### 4.3 AI 활용 — "인수인계 AI" 하나에 집중

실제 공무원 **사무인계인수서**의 항목은 `담당업무 현황` / `진행 중인 사항` / `미결 사항` / `인계 시 유의사항`이다. 이 항목들은 지금까지 **떠나는 사람이 마지막 주에 기억으로 급조**해왔다.

이음에는 그 재료가 이미 축적되어 있다. 업무 카드의 진행상태·메모·변경이력·첨부문서가 그대로 저 4개 항목에 대응한다.
**AI는 그것을 읽어 문서로 조립하는 역할만 한다.**

출력 3종:
1. 사무인계인수서 초안 생성
2. 미결사항 자동 추출
3. 후임자용 3줄 브리핑 (업무 카드 진입 시)

> 억지로 끼워넣은 AI가 아니라, **이 제품이 아니면 애초에 불가능한 AI**다.

### 4.4 연간 주기 소환

공무원 업무는 연 단위로 반복된다(예산편성, 정기행사, 점검, 정산). 실질적인 인수인계는 **"작년 담당자가 이맘때 무엇을 어떻게 했는가"**다.
`work` 테이블에 `previous_year_work_id`를 두어 **작년 같은 업무를 연결**하고, 대시보드에서 "작년 이맘때" 위젯으로 소환한다.

## 5. 차별성

### 5.1 예상 질문과 답변

> **Q. 노션이나 구글 독스 쓰면 되는 것 아닌가요?**

**A. 쓸 수 없습니다.** 망분리와 공공자료 외부반출 제한 때문입니다. 문제는 "민간에 이미 있다"가 아니라 **"민간 도구를 쓸 수 없는 조직에 아무것도 없다"**는 것입니다.

> **Q. 온나라시스템과 중복 아닌가요?**

**A. 대체가 아니라 보완입니다.** 온나라는 **결재와 공문** 중심의 문서 시스템이고, 이음은 **결재 이전 단계의 실무 협업**을 다룹니다. 지금 그 단계는 개인 PC와 메신저에 있습니다.

> **Q. 그냥 트렐로 아닌가요?**

**A.** 트렐로에는 **인사이동 시 업무 일괄 이관**도, **작년 담당자 기록 소환**도, **행정 감사에 대응하는 열람 로그**도 없습니다. 이 세 가지는 공공 조직 고유의 요구입니다.

### 5.2 경쟁 지형

24개 과제 중 대부분은 지도·추천·대시보드 등 **시민 체감형**이다. 화면은 화려하지만 심사자(공무원) 입장에서는 남의 이야기다.
반면 내부 행정혁신형은 **심사자 본인의 고통**이다.
- 강점: 공감도 100%
- 약점: **데모가 밋밋해 보이기 쉬움** ← 이 약점을 인수인계 시연으로 뒤집는다

## 6. 시스템 설계

### 6.1 기술 스택

| 층 | 선택 |
|---|---|
| 프론트/서버 | **Next.js (App Router)** — 화면 + Server Actions + AI 프록시 API Route |
| 데이터 | **Supabase** — Auth / Postgres + RLS / Realtime / Storage |
| AI | **Claude API** (서버에서만 키 사용, 교체 가능한 인터페이스로 추상화) |
| 배포 | **Vercel** |
| UI | shadcn/ui (Radix) + **KRDS 디자인 토큰** |

### 6.2 데이터 모델

| 테이블 | 내용 | 대응 요구사항 |
|---|---|---|
| `department` | 부서 (화성시 조직도 기반) | 부서 간 |
| `profile` | 공무원 (이름·소속·직급) | — |
| **`work`** | **업무 카드** — 제목·설명·상태·기한·주담당·연차·`previous_year_work_id` | 진행상태 관리 |
| `work_member` | 업무 참여자 + 역할(소유/편집/열람) | **접근권한 관리** |
| `document` | 업무에 속한 문서 (섹션 분할 본문 / 첨부파일) | 문서 공유·공동편집 |
| `doc_version` | 저장 시 스냅샷 | **변경이력 기록** |
| `activity` | 모든 사건 로그 (append-only) | 협업 이력 관리 |
| `comment` | 업무 카드 내 대화 | 협업 |
| `handover` | 인계 세션 (전임자→후임자, 대상 업무, 생성 인계서) | 인수인계 |

### 6.3 아키텍처

```
Next.js (App Router)  ──►  Supabase
  · 화면 + Server Actions      · Auth        (부서 계정)
  · /api/handover (AI 프록시)  · Postgres + RLS  ← 권한을 DB가 강제
                               · Realtime    ← 실시간 공유
                               · Storage     ← 첨부파일 (private)
         │
         └──►  LLM  (서버 전용 / 인터페이스 추상화 → 내부망 sLLM 교체 가능)
```

### 6.4 실시간 공동편집에 대한 판단

진정한 동시 편집(CRDT)은 13일 일정에서 위험이 크다. 따라서 단계적으로 접근한다.

- **1차예선** — 문서를 **섹션 단위로 분할**. 편집 중 섹션 잠금 + `편집 중` 표시 + 저장 시 즉시 반영 + 접속자 아바타
  → 화면상 충분히 실시간 협업으로 인식되고, **충돌이 원천적으로 발생하지 않아 시연이 안전**하다
- **2차예선** — 여력이 있으면 Tiptap + Yjs로 동시 타이핑까지 확장

## 7. 보안 설계

공문서를 다루는 시스템이므로 보안은 부가 요소가 아니다. **두 층으로 분리해 설계한다.**

| | 층 1: 시제품 | 층 2: 실제 도입 설계 |
|---|---|---|
| 환경 | 공개 인터넷 (Vercel + Supabase) | **내부 업무망 온프레미스** |
| 데이터 | **100% 가상 데이터** | 실제 공문서 |
| 목적 | 작동 증명 | 행정 적용 가능성 증명 |

> **원칙: 시제품에는 실제 공문서를 단 한 건도 넣지 않는다.** 발표 시 이 사실을 먼저 밝힌다.

### 7.1 인증

- **Supabase Auth** 사용 — 비밀번호 해시를 직접 구현하지 않음
- 공무원 메일 **도메인 화이트리스트**를 서버(Auth Hook)에서 강제
- **MFA(TOTP)** 2단계 인증
- 로그인 시도 **rate limiting** (brute force / credential stuffing 차단)
- 세션은 `httpOnly` + `Secure` + `SameSite` 쿠키 (JWT를 localStorage에 두지 않음)
- **30분 무동작 자동 로그아웃**

### 7.2 인가

- 모든 테이블 **RLS `default deny`**. 명시적으로 허용한 정책만 통과
- **Service Role Key는 서버 전용.** Server Action에서도 사용자 세션 기반 클라이언트를 사용하며 service role로 우회하지 않음
- **IDOR 차단** — URL에 UUID가 노출되어도 RLS가 차단. 앱 코드 버그가 곧바로 유출로 이어지지 않는 구조
- 첨부파일 — Storage 버킷 `private` + **단기 만료 signed URL**

### 7.3 감사 추적

- `activity` 로그를 **DB 트리거로 자동 기록** (앱 코드 우회 불가)
- **UPDATE/DELETE 정책이 없는 append-only 테이블** — 로그 조작 불가
- **열람 로그까지 기록.** 공문서는 "누가 수정했는가"만큼 **"누가 열람했는가"**가 중요하다

### 7.4 애플리케이션 취약점

| 위협 | 대응 |
|---|---|
| XSS | 리치텍스트 본문 서버 sanitize + CSP 헤더 |
| CSRF | SameSite 쿠키 + Server Action origin 검증 |
| SQL Injection | Supabase 클라이언트만 사용, raw SQL 금지 |
| 파일 업로드 | MIME·확장자 검증, 용량 제한, 실행파일 차단 |
| 헤더 | CSP / HSTS / X-Frame-Options DENY / nosniff |
| 의존성 | Dependabot + `npm audit` |
| **키 유출** | **제출물에 깃헙 주소가 포함되므로 최우선 관리.** `.gitignore` 선행 설정 + 커밋 전 시크릿 스캔 |

### 7.5 AI 구간

공문서 내용을 외부 LLM API로 전송하는 것 자체가 공공에서는 제약 사항일 수 있다. 이를 먼저 짚고 답을 제시한다.

- 시제품 — 가상 데이터 + 서버 프록시 + 전송 전 **개인정보 패턴 마스킹**(주민번호·연락처·주소)
- 프롬프트 인젝션 방어 — 문서 본문을 시스템 지시와 분리, 출력 검증
- **핵심** — AI 호출을 인터페이스로 추상화하여, 실제 도입 시 **내부망 sLLM으로 모델만 교체**하면 되도록 설계

> *"AI 기능은 모델 교체 지점을 분리해 두었기 때문에, 내부망 전용 모델로 전환해도 코드 변경이 없습니다."*

### 7.6 실제 도입 시 (로드맵)

- **내부 업무망 온프레미스 배포** — Supabase self-host + Next.js standalone. 망분리 환경에서 외부 인터넷 호출 0건으로 동작
- **CSAP(클라우드보안인증)** 획득 클라우드 또는 시청 자체 서버
- **GPKI 행정전자서명 연동** — 공무원 인증서 로그인
- **개인정보 영향평가(PIA)** 대상 여부 검토
- **국정원 보안적합성 검증** 절차 반영

## 8. 디자인 시스템

### 8.1 원칙

> 실제로 시청에 도입되어도 이상하지 않으면서, 기존 관공서 시스템보다 명확히 잘 만들어진 것.

화려함이 아니라 **밀도와 일관성**으로 완성도를 만든다.

### 8.2 KRDS에 대한 입장

「디지털 정부서비스 UI/UX 가이드라인」과 KRDS는 **법령이 아닌 권고**이며, 1차 적용 대상은 대국민 서비스다. 우리는 로그인 기반 내부 업무 시스템이므로 **전면 준수 대상이 아니다.**
그러나 체크리스트 자체가 `E(예외)` `N/A(해당없음)` 판정 칸을 두고 있으므로, **취사선택하고 그 판단 근거를 문서화**한다.

> 발표 입장: *"준수했습니다"가 아니라 **"검토하고 취사선택했습니다"**.*

**층별 결정**

| 층 | 선택 | 이유 |
|---|---|---|
| 디자인 토큰 | **KRDS 값 채택** | 비용 없이 "정부 서비스다운" 인상 확보 |
| 컴포넌트 구현 | **shadcn/ui (Radix)** | 13일 일정에 속도 + 키보드/포커스/ARIA 기본 제공 |
| 레이아웃 | **업무 도구형** (좌측 사이드바 + 상단 컨텍스트바) | 대국민 사이트 구조는 부적합 |
| 접근성 | **실질 준수** | 유일한 법적 의무 영역 |

### 8.4 이음 고유 시각 언어 3종

완성도는 화면 수가 아니라 **반복되는 시각 언어**에서 나온다.

1. **상태 배지** — `대기 / 진행중 / 검토 / 완료 / 지연`. 제품의 중심 색 언어
2. **이력 타임라인** — 세로 타임라인 + 행위자 아바타 + 변경 diff. `협업 이력 관리` 요구사항의 시각적 증거물
3. **참여자 아바타 스택 + 실시간 표시** — 화면에 협업감을 만드는 유일한 장치

### 8.5 적용하지 않는 것

공식 배너 · 운영기관 식별자 · 대국민형 헤더/푸터 구조 · 브레드크럼/페이지네이션(필요 화면 한정) · 다크모드 · KRDS 컴포넌트 킷 코드 자체

### 8.6 배제 목록 (완성도 저해 요소)

보라-파랑 그라데이션 / 글래스모피즘 / 이모지 아이콘 / 대시보드 히어로 섹션 / 불필요한 일러스트 / 과한 그림자

## 10. 기대효과 및 행정 적용방안

### 10.1 확산 가능성

부서·업무 분류 테이블만 교체하면 **경기도 31개 시·군, 전국 243개 지자체**에 그대로 적용 가능한 구조로 설계한다. 지자체마다 새로 구축할 필요가 없다.

### 10.2 행정 비용 절감 (측정 가능한 정의)

인사이동으로 인한 업무 재파악 시간을 절감 지표로 정의한다.

```
화성시 공무원 수 × 연간 인사이동률 = 연간 신규 업무 파악 인원
연간 신규 업무 파악 인원 × 1인당 절감 시간 × 시간당 인건비 = 연간 절감액
```

> **주의 —** 위 계산에 들어갈 실제 수치(공무원 수, 인사이동률, 인건비 기준)는 **반드시 출처를 확인해 각주로 명시한다.** 근거 없는 추정치를 발표에 넣으면 역풍을 맞는다. 13장 참조.

### 10.3 KRDS 자체 검증 결과

「디지털 정부서비스 UI/UX 가이드라인 자체 검증 체크리스트」(2024.11) 기준으로 자체 검증을 수행하고 결과서를 첨부한다.

- 전체 체크리스트 311개 (스타일 21 / 컴포넌트 170 / 기본패턴 47 / 서비스패턴 73)
- 적용 트랙: **자체 상징** (화성시 CI 사용) → 적용 대상 301개에서 시작
- 검증 환경: Windows 10+ / Chrome 최신 / 1920×1080 / 확대 100%
- 검증 범위: **화면 10개 이상 표집** (지침 권장)
- 판정: `P` / `F` / `E` / `N/A`
- **목표: 적용 대상 항목 준수율 90%**

> 발표에서는 「행정 적용 가능한 제안」 섹션의 **근거 슬라이드 1장**으로만 사용한다. 주인공은 어디까지나 협업 문제 해결이다.
